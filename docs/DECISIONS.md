# Design Decisions

Every meaningful design decision gets an entry. Format:

```
### D-###: <title>
- Context: what problem we were solving
- Options considered: 2-3 real alternatives
- Decision: what we picked
- Tradeoff: what we gave up, and when we'd revisit
```

---

### D-001: Monorepo
- Context: CageOps has several Python services (scraper, worker, api, trainer), shared code (db models, config), a Next.js frontend, and infra manifests. We needed to decide how to lay out the repositories.
- Options considered:
  1. One repo per service, with shared code published as a package.
  2. A monorepo that uses git submodules for shared code.
  3. A single monorepo with all services, shared code, web and infra together.
- Decision: a single monorepo (option 3). Shared code lives in `packages/cageops_common` and is consumed directly by each service through the uv workspace.
- Tradeoff: one CI pipeline and atomic cross-service changes (one PR can change a shared model and every service using it), in exchange for coarser access control and CI time that grows with the repo. Revisit if separate teams or deploy cadences emerge; then path-filtered CI or splitting a service out becomes worth it.

### D-002: uv for Python packaging and workspace
- Context: we need to install Python 3.12, manage dependencies for five packages with one shared local package, and get reproducible installs in CI and Docker.
- Options considered:
  1. uv (workspaces, single lockfile, manages Python versions).
  2. Poetry (mature, but workspace support is weaker).
  3. pip + venv + pip-tools (most familiar, but no workspace concept and more manual steps).
- Decision: uv. One `uv.lock` pins every package in the workspace. Services depend on `cageops-common` via `{ workspace = true }`, and `uv sync --locked` in CI fails if the lockfile is stale.
- Tradeoff: uv is newer, with less community history than pip or Poetry, and we pin the version in CI to limit surprises. Revisit if a workspace limitation gets in the way of building per-service Docker images (Phase 2b).

### D-003: PostgreSQL 16 (not 17)
- Context: we need one Postgres major version for local dev now and production later, with the pgvector extension for embeddings in Phase 4.
- Options considered:
  1. PostgreSQL 16 with the `pgvector/pgvector` image.
  2. PostgreSQL 17.
  3. Defer the choice to whichever managed Postgres we pick later.
- Decision: PostgreSQL 16. It's what the project spec calls for, it's mature, and pgvector images for it are well tested. 17's improvements (vacuum and memory efficiency, incremental backup) don't matter at our data size.
- Tradeoff: we give up 17's newer features and a slightly longer support window. Revisit before the production deploy (Phase 2c/6), or sooner if a needed feature or pgvector release requires 17. A major upgrade is a dump/restore, which the Phase 6 backup work will exercise anyway.

### D-004: ufcstats.com access policy
- Context: the data source audit (docs/DATA_SOURCES.md) couldn't retrieve robots.txt. A manual check on 2026-10-01 found that `http://ufcstats.com/robots.txt` returns 404 (no crawl rules published), and the site footer has no terms of use or any language about scraping.
- Options considered:
  1. Scrape with no safeguards, since no rules exist.
  2. Scrape politely anyway.
  3. Don't scrape; rely only on Kaggle snapshots.
- Decision: scrape politely anyway (option 2). The limits are ~1 request/second globally, shared across all workers; a raw HTML cache so pages are never re-fetched unless forced; and a descriptive User-Agent with a contact email. The scraper fetches robots.txt on startup and treats a 404 as "allowed", but would honor any rules or Crawl-delay that appear later.
- Tradeoff: the absence of terms is not permission, so some legal and ethical risk remains. A slower backfill is the cost of being polite. Revisit if the site adds terms or robots rules, or if we get contacted.

### D-005: Drop the ESPN MMA API as a data source
- Context: the audit found that the Disney Terms of Use explicitly prohibit automated extraction and use of content for AI/ML training, testing, or benchmarking, and limit use to personal, noncommercial. The endpoints are also undocumented and unstable.
- Options considered:
  1. Use ESPN anyway.
  2. Use it for the non-ML parts only.
  3. Drop it.
- Decision: drop it (option 3). Everything it offered (results, stats, odds, rankings) is covered by ufcstats plus the Kaggle datasets. "ESPN MMA API" is removed from the architecture diagram in CLAUDE.md.
- Tradeoff: we lose a redundant source and a possible live-odds feed. Revisit only if ESPN publishes an official API with permissive terms.

### D-006: Seed data strategy
- Context: several Kaggle UFC datasets exist, and some ship precomputed rolling features that we can't prove are point-in-time correct (CLAUDE.md rule 1).
- Options considered:
  1. One all-in-one dataset with precomputed features.
  2. The mdabbert dataset for everything.
  3. Raw facts from the jerzyszocik "silver" file, plus separate odds and rankings sources.
- Decision: option 3. Stats come from jerzyszocik silver (raw per-round facts, the same shape the scraper produces). Odds come from mdabbert (CC BY 4.0), used as a baseline only and never as model features. Rankings come from the jerzyszocik rankings history. The "golden" precomputed features are NOT loaded.
- Tradeoff: more loaders and a join across sources, in exchange for a single raw schema shared by seed and scraped data and a leakage test that actually means something. Revisit if silver turns out to lack per-round columns or has bad date coverage.

### D-007: Reproducible seed downloads with a sha256 manifest
- Context: the seed datasets are Kaggle files that their authors refresh (rankings weekly, odds daily). Kaggle's CLI can't download an older version of a dataset and doesn't expose a version number, so "the data we loaded" can't be re-fetched later and row counts could silently change between pulls.
- Options considered:
  1. Download by hand once and document it in prose.
  2. Script the download and record Kaggle's version or last-updated date.
  3. Script the download and fingerprint every file we actually use with a sha256 manifest.
- Decision: option 3. `scripts/download_seed.sh` fetches only the files we load (listed in `scripts/seed_sources.json`), verifies each one actually landed (unzipping if Kaggle sent a `.zip`), and `scripts/write_manifest.py` writes `data/raw/MANIFEST.json` with size, sha256, download time, Kaggle's file creation timestamp, and license. A copy is committed as `docs/seed_manifest.json` (hashes and dates only, no data) so any row count in the docs can be tied to exact input bytes. Existing files are always re-hashed, `--force` re-downloads, and a missing file is an error, so the manifest can't describe something that isn't there.
- Tradeoff: we can detect that the data changed but can't recover the old data (Kaggle won't serve it), so reproducing an old result means keeping a local copy of `data/raw/`. The Kaggle CLI is pinned (2.2.4) because its behavior has changed between releases. Revisit if we need true archival: then store the raw files in our own object storage keyed by sha256.

### D-008: Amend D-006, what we load from the silver file
- Context: D-006 assumed the jerzyszocik silver file was raw fight facts only. Profiling it (docs/DATA_SOURCES.md, "Silver Parquet findings") showed it also contains (a) scrape-time career stats per fighter (`SlpM`, `Str_Acc`, `TD_Def`, ... and the `w`/`l`/`d` record) filled for every fight, (b) odds columns with no capture date, and (c) a `ranking` column with no as-of date.
- Options considered:
  1. Load everything silver offers and use it.
  2. Load only fight facts and per-round stats from silver, and treat the rest as untrusted.
  3. Drop silver and rebuild everything from scraping.
- Decision: option 2. Point-in-time correctness means a feature for a fight may only use what was known strictly before that fight. A career stat scraped in 2026 includes every fight a fighter had after 2019, so using it for a 2019 fight lets the model see the future (the answer is baked into the input). Silver's odds and rankings have no capture date, so we can't prove they pre-date the fight. Therefore: (a) silver's career stats and record are not loaded as features; the feature pipeline computes everything from per-round facts, (b) silver's odds are loaded into the `odds` table with `source='silver'` and a null `captured_at`, next to mdabbert's (`source='mdabbert'`); mdabbert is the primary baseline because it is built from bestfightodds and meant to be pre-fight, and silver only fills gaps if the two agree on the favorite at a high rate (measured in the Phase 1a plan), (c) silver's `ranking` column is ignored; rankings come from `UFC_rankings_history.csv` with an as-of join (each fighter's latest rank strictly before the fight date). Odds are never model features (baseline only), per D-006.
- Tradeoff: more loaders and a source column to carry through, and we discard columns that would have been convenient. In exchange the leakage test has something real to prove. Revisit if a source documents when its odds or rankings were captured.

### D-009: Fight schema conventions (order, corner, cleaning)
- Context: silver puts the winner in slot 1 in 64% of fights (slot 1 is the red corner, and red wins 64.2% in the loaded data), so slot order carries information. Silver also has messy values: whitespace-padded results, the literal string "NULL", title names in the weight-class column.
- Options considered:
  1. Keep silver's f_1/f_2 order as row order.
  2. Store fighters in a neutral order and drop corner entirely.
  3. Store fighters in a neutral order and keep corner as a separate, nullable raw fact.
- Decision: option 3. `fights.fighter_a_id < fighter_b_id`, with fighter ids assigned in ufcstats-id order at seed time, so row order is unrelated to the outcome (checked on real data: winner is fighter_a in 50.1% of fights, red is fighter_a in 50.3%). The winner is `winner_id`, never "A/B". Corner is `red_fighter_id` (nullable): it is assigned before the fight, so it is a legitimate pre-fight fact, and the leak was only ever slot order used as row order. The loader stores raw facts; Phase 1c decides whether corner becomes a feature. ufcstats-derived data (silver) is canonical for corner and winner, and only silver creates rows in `fights`; mdabbert is cross-checked against it (6 red-corner and 2 winner disagreements are logged in the load report; the two winner disagreements were checked by hand against the official result and are mdabbert errors: Davis beat Jones by unanimous decision, and Jandiroba beat Martin) and its 14 unmatched fights (e.g. Hall vs Souza, cancelled) are reported and skipped. Cleaning rules, each covered by a table-driven test over every observed raw value, where an unknown value fails the load: whitespace collapsed in `result`; Doctor's Stoppage maps to `ko_tko` with the detail kept in `method_detail`; a bare "Decision" takes its type (unanimous/split/majority) from the details column; scheduled rounds of 0 become NULL; the literal strings "NULL" and "" become NULL; `weight_class` is nullable (10 early fights and one "Nieznana" are unknown); 17 recent title fights that carry the title name in the weight-class column are mapped to their division with `is_title_fight` set; fights with no per-round data (21, all from 1994 to 1998) get `has_round_stats = false` and no rows, never zeros.
- Tradeoff: fighter ids follow ufcstats-id order only for the seed fighters, so fighters added later by the scraper get larger ids and `fighter_a` is then "the seed fighter" more often than chance (training swaps order randomly, so this is cosmetic). Revisit if a model ever uses row order. Silver's red-corner inference (slot 1 = red) is confirmed by mdabbert in 7,154 of 7,160 matched fights.

### D-010: Name resolution, source-scoped aliases, and matching rules
- Context: odds and rankings identify fighters by name only, and names differ between sources ("Kai Kara-France" vs "Kai Kara France", "Bobby Green" vs "King Green"). Silver has 2,686 fighters but one name that belongs to two people (Bruno Silva, a middleweight and a flyweight).
- Options considered:
  1. Exact string match, drop the rest.
  2. Fuzzy matching that picks the closest name.
  3. Normalized-name match, evidence-based reviewed aliases scoped per source, and never guessing when ambiguous.
- Decision: option 3. Names are normalized (accents stripped, punctuation dropped). A name matching more than one fighter is narrowed by weight class and active dates, and if still not unique it is left unmatched and listed; it is never guessed (tested with two same-name fighters). Aliases are keyed `(source, alias_norm)`, so an alias reviewed for mdabbert rows never resolves a name from rankings, where "Tim Johnson" or a bare "Derrick" could be someone else. The 124 aliases are committed in `aliases.csv`: 96 for mdabbert, each backed by an opponent-and-date match and reviewed by hand, and 28 for the two rankings sources. Rankings have no opponent to check, so a reviewed alias there needed a rule: the candidate must match the ranked division and have fought within about 12 months of every snapshot where the name appears (this accepted `Tim Johnson` as Timothy Johnson, a heavyweight ranked in 48 snapshots, and `Luis Henrique Barbosa` as Luis Henrique). Two candidates were rejected by hand as different people: `Jaime Alvarez` (only similar to Joel Alvarez) and the closest spelling for `Antonio Rogerio Nogueira`, which is Minotauro (a heavyweight) when the ranked fighter is Rogerio Nogueira, "Lil Nog", a light heavyweight. mdabbert rows match a fight on exact date first, then +/-1 day for cards that cross midnight; on the real data 7,160 of 7,177 rows (99.76%) matched on the exact date and none needed the fallback. Unmatched rows are kept with a null fighter and listed in the load report.
- Tradeoff: every new source needs its own reviewed alias list, and unreviewed candidates stay unloaded. Remaining misses: 3 mdabbert names (a typo, a fighter missing from silver, and one ambiguous Bruno Silva fight), 14 fights mdabbert has that silver does not (reported and skipped), and 3 ranking names (0.51% of jerzyszocik's, 0.32% of martj42's). Revisit if a source ships fighter ids.

### D-011: Rankings sources, snapshot quality, and the as-of rule
- Context: `UFC_rankings_history.csv` (jerzyszocik) is clean through 2025-07-27, but all 63 weekly snapshot dates from 2025-08-03 to 2026-10-01 contain two lists merged under one date (a fighter appears at two ranks, e.g. 28 rows for 17 fighters in Women's Bantamweight on 2026-10-01), and the file is sorted by rank so the lists can't be separated. Snapshot dates also fall on different weekdays across eras (Monday, Tuesday, Sunday, Thursday), so they look like the author's scrape schedule, not the UFC's publish date. Across 70 title changes, the new champion first appears 2 to 30 days after the event and never on or before it.
- Options considered:
  1. Load everything with a quality flag and filter later.
  2. Load only clean snapshots, and fill the gap from a second source if one is clean.
  3. Scrape the official rankings page ourselves for the missing period.
- Decision: option 2. A snapshot date is skipped entirely if any fighter appears twice in one list (the raw file stays on disk and in the manifest). martj42/ufc-rankings (CC0) is loaded as a second source: 530 clean dates through 2026-06-02 (2 dates skipped for the same reason). The view `fight_pre_rankings` uses only snapshots dated strictly before the fight, returns a NULL rank (status `stale`) if the latest snapshot is more than `RANKING_MAX_AGE_DAYS = 21` days old (a named constant with a test that checks the view definition), and prefers a fresh jerzyszocik snapshot over a fresh martj42 one. Snapshot dates that are late only make ranks staler, never leak, because a scrape date is never earlier than the publish date: that is the safe direction for a strictly-before join. Other rules: vacant-title rows (empty or "NA" names) are skipped, and the bare "Pound-for-Pound" list, which runs 2013-02-04 to 2020-01-20 before women's pound-for-pound existed, is treated as the men's list.
- Tradeoff: no ranking data for fights after about 2026-06-23 (martj42 ends 2026-06-02, plus the 21-day cap), which includes every upcoming fight we want to predict, so Phase 1b needs a live rankings source. The two sources disagree on about 5% of rows for the same older dates, so the view never mixes them within one snapshot. Revisit when a live source exists.

### D-012: Integration tests run against real Postgres, including in CI
- Context: the loaders rely on `INSERT ... ON CONFLICT`, CHECK constraints, a SQL view, and `CREATE EXTENSION vector`, which SQLite doesn't behave like.
- Options considered:
  1. SQLite in-memory for tests.
  2. Mock the database layer.
  3. A real Postgres (the same pgvector image as local dev) for integration tests, locally and as a CI service container.
- Decision: option 3. Tests build a separate `cageops_test` database from the Alembic migrations (so migrations are exercised on every run) and truncate tables between tests. Locally they skip with a clear reason if Postgres is unreachable; in CI `REQUIRE_DB=1` makes an unreachable database a failure so tests can't be silently skipped. Fixtures are tiny and built inside the tests; the full-dataset load stays local, because `data/` isn't in CI.
- Tradeoff: CI takes longer and needs the Postgres service, and tests share one database so they can't run in parallel. Revisit if the suite grows slow (per-worker databases).

The Kaggle silver file is still dated 2026-06-10, so no compliant source exists for June to October 2026 fight stats.
- Options considered:
  1. Solve the challenge in code, or run a headless browser that solves it.
  2. Pause Phase 1b until the operator replies.
  3. Build the whole pipeline now against hand-saved fixtures and a local replay server, treat the challenge as a stop signal, and ask the operator for access.

### D-014: Global rate limit as an atomic next-slot reservation in Redis
- Context: CLAUDE.md rule 2 caps us at about 1 request/second against ufcstats, shared across every worker. Workers are separate processes (and later separate pods), so the limit has to live somewhere they all see: Redis.
- Options considered:
  1. Read the "next allowed time" key, check it, write it back (GET then SET). This is a race: two workers read the same value in the same millisecond, both see a free slot, both write, and both fetch at once. Reproduced under 8 threads: 26 of 40 slots were double-booked.
  2. A token bucket in a Lua script. Correct, but it allows bursts (we don't want any), keeps two pieces of state (tokens and last refill) and needs refill math, and a caller without a token has to poll and come back.
  3. A Lua script that reserves the next slot: read `next_allowed`, take `max(now, next_allowed)` as my slot, store `slot + interval`, return the slot and the wait. The caller sleeps until its slot.
  (A fixed-window counter was also rejected: it allows two requests 1 ms apart across a window boundary, so it limits volume, not spacing. WATCH/MULTI works too but retries in a loop under contention.)
- Decision: option 3. Redis runs one script at a time, so the read and the write can't be interleaved. It is about 8 lines, first come first served, with no polling. Time comes from Redis `TIME` inside the script, not the worker's clock, so containers with drifting clocks still agree. The script returns the absolute slot (ms) as well as the wait, so the concurrency test asserts on slots (all distinct, at least one interval apart) and can't flake on client timing. One key per source (`ratelimit:{source}`), so the replay source has its own limit. A 429 with `Retry-After` calls `penalize()`, which moves the next slot out for all workers. If Redis is down no slot can be taken, so the fetcher sends nothing (fails closed).
- Tradeoff: every request costs a Redis round trip, which is negligible at 1 req/s. A worker waiting for its slot holds its job while it sleeps, so many workers all queue behind one limiter and add nothing: that is the bottleneck the Phase 1b benchmark measures. Spacing is per request, not per second, so we never burst even after being idle. Redis eviction of the key would reset the limit, so production Redis needs `maxmemory-policy noeviction`. Revisit if a source allows bursts (then a token bucket fits) or a second limit tier is needed (per path).

### D-015: Raw HTML cache policy by page type, with the replay source kept separate
- Context: CLAUDE.md says never re-fetch a cached page unless forced. But some pages change: a card gets bouts added or cancelled, results post on fight night, stats are sometimes corrected the next day, fighter bios get edited. "Cache forever" would freeze wrong data; "never cache" would break politeness and the benchmark.
- Options considered:
  1. Cache everything forever; `--force` to refresh.
  2. A single TTL for every page.
  3. A freshness rule per page type (a Source method), with finished events and fights treated as immutable once they have had time to settle.
- Decision: option 3, stored in `raw_pages` (one row per URL, latest copy, only 200 and 404 are kept). Fight and event pages: fresh for 6 hours, and final for good once fetched 3 or more days after the event date (the job always knows the event date, which also comes from the event page, not the fight page). Event date unknown: 6 hours. Fighter pages: 30 days (we keep only bio fields). Completed events list: 12 hours. Upcoming events list: 6 hours. robots.txt: 24 hours (RFC 9309's maximum). Any 404: 1 day (the page may appear later). Server errors, 429s and bot-challenge pages are never cached: caching them would hide the real page behind a bad copy. `--force` skips the cache read only; it still obeys the circuit breaker and rate limiter and still writes the new copy. A cache hit returns before the rate limiter, so a warm run never waits on it. The replay server (checkpoint 5) is its own source name, `ufcstats_replay`, with its own base URL from env: its pages are stored with `source='ufcstats_replay'` and are never served to the real source, it has its own limiter key (`ratelimit:ufcstats_replay`) and breaker key (`breaker:ufcstats_replay`), and the code refuses to pair the name `ufcstats` with a non-ufcstats host (or the replay name with the real host), so benchmark data can't be filed as live data.
- Tradeoff: a stats correction posted more than 3 days after an event is missed unless someone forces a refetch. 3 days is a guess; revisit if the checkpoint 3 seed-versus-scrape comparison shows late corrections. Storing full HTML in Postgres costs space (about 60 KB a page, so roughly 100 MB for the whole history) in exchange for being able to re-parse without the network, which the warm benchmark relies on. Revisit if the table grows large (object storage keyed by hash).

- **Amendment 2026-10-03, known limitation: overturned results.** A fight's result can change weeks or months after the event (a win overturned to a no contest after a failed drug test or an appeal), but this policy treats a fight or event page fetched 3 days after the event as final and never fetches it again, so an overturn after that window is invisible to us. Consequences: our `fights` row, any Phase 5 prediction graded against it, and every later fight's features built from it would be wrong until corrected. Proposed fix, for later (Phase 6 scheduling, and required before Phase 5 grades anything): a periodic forced refresh of the last ~6 months of completed events, `backfill --since <today - 6 months> --force` (the `--force` flag already exists, so this is no new code): about 22 events at about 13 requests each is roughly 300 requests, about 5 minutes at 1 request/second, run weekly as a CronJob. Fighter pages aren't refreshed (30-day TTL, bio only), and older history can be refreshed on demand. What D-019 adds so a refresh is safe and visible: the result columns are replaced as a unit including NULLs (so an overturn clears the old winner) and every change to a completed fight's result is logged and counted as a `result_changed` anomaly. Downstream rules for later phases: Phase 5 re-grades a prediction when `result_changed` fires, and the Phase 1c "rebuild features from scratch" command is how corrected results reach features.

### D-016: robots.txt handling, error classes, and a manual circuit breaker
- Context: the scraper must check robots.txt on startup and refuse to run if a path it needs is disallowed. Separately, it must tell errors worth retrying from ones that aren't, and it must never hammer a site that has just blocked it (D-013).
- Options considered:
  1. Treat a missing or unreadable robots.txt as "allowed".
  2. Follow RFC 9309: 4xx means no rules, 5xx or unreachable means assume disallowed.
  3. For the block signal: let the normal retry logic handle it, or auto-reset the breaker after a cooldown, or require a human to reset it.
- Decision: option 2 for robots.txt (today ufcstats returns 404, which means no rules; our own 1 req/s limit still applies). A `Crawl-delay` longer than our default replaces the default; we parse it ourselves because the standard library only reads whole numbers, and the most specific group wins with no inheritance from `*`. The check runs through the same Fetcher (rate limited, cached 24 hours) at every start. Error classes: timeouts, connection errors, 5xx and 429 are retryable (429 also backs every worker off); 404 and other 4xx, cross-site or over-long redirects and parse errors are permanent; a challenge page or 403 is neither: it opens a circuit breaker that stops all workers, is never cached or retried, and has no timer. A person closes it after checking what the site is doing (`reset`, with a CLI command in checkpoint 4). Same-site redirects (including http <-> https on ufcstats.com) are followed by running the whole fetch path again on the `Location` URL, so every hop goes through the cache, the breaker and the rate limiter and costs its own slot; at most 3 hops, then a permanent error (this also ends redirect loops). A redirect to another host is a permanent error and the other host is never contacted, because a hop that left the site would skip the robots and rate-limit checks. The `Location` is logged on every 3xx. After a followed redirect the final page is also filed under the originally requested URL, so asking for it again is a cache hit rather than another round trip. The breaker is checked before taking a rate-limit slot and again after waiting for it, so a worker queued behind the one that tripped it sends nothing.
- Tradeoff: a human has to notice and reset the breaker (a metric, `scraper_source_blocked_total`, is there for alerting in Phase 6), so a false positive stops ingestion until someone looks. We accept that: probing a site that told us to go away is the thing we promised not to do. Treating other 4xx on robots.txt as "no rules" follows the RFC but is permissive; revisit if a source's 403 on robots.txt should instead count as a block (today 403 already trips the breaker).

### D-017: Fixtures: full pages stay local, only mechanically minimized copies are committed
- Context: parser tests need real ufcstats HTML (CLAUDE.md: test against saved fixtures, never live requests). But DATA_SOURCES.md section 5 says to "store facts (numbers, results), not page layouts; don't redistribute raw HTML", and the repo is public. Committing 12 whole pages, with their scripts, styles, navigation and ads, would be redistributing the site's pages.
- Options considered:
  1. Commit the full hand-saved pages.
  2. Hand-write synthetic HTML that imitates the structure. Nothing is redistributed, but it only tests what we guessed the markup looks like, which is the thing the tests are meant to check.
  3. Keep the full pages in `data/fixtures/ufcstats/` (gitignored) and commit only copies with everything the parsers don't read deleted, by a script that can only delete.
- Decision: option 3. `scripts/minimize_fixture.py` finds where scripts, styles, noscript, iframes, ad slots (`<ins>`), inline SVG, `<nav>`, `<footer>`, `<link>` tags and comments start and end in the saved text and cuts those ranges out. It never re-serializes: every remaining character is exactly as saved (tags, attribute order and quoting, classes, entities, whitespace, line endings), so the fixture is still what the scraper would really receive. It checks that the output is the input with deletions only, refuses a bot-challenge page, refuses an unclosed element rather than guessing, and never overwrites its input. More can be removed with `--remove-tag/--remove-class/--remove-id` once the parsers show what they never read. Only the minimized files go to `services/scraper/tests/fixtures/ufcstats/`.
- Tradeoff: the committed files still hold the facts we need (names, numbers, results) and the tag and class structure of the parts we parse, so this reduces redistribution to the minimum the tests need but does not eliminate it. It is a small number of pages, factual content, kept for testing, but it is a judgment call. If the operator objects (the email asked for permission), replace them with synthetic fixtures built from the same structure, or drop the committed copies and keep them local. Because the full pages are not in git, a fresh clone can't regenerate the minimized ones; the minimized files are the source of truth in the repo, and the full pages are Ari's local copy.

### D-018: Parsers: pure functions that return the page's own words, with loose layout checks
- Context: Phase 1b turns ufcstats HTML into rows that line up with the Phase 1a seed. The pages have traps (see DATA_SOURCES.md, "ufcstats page structure"): the event page lists the winner first, the fight page lists the red corner first and has no date, the per-round table nests `<thead>` rows inside `<tbody>`, the totals header has a duplicated "Td %", the fighter page mixes bio facts with "as of today" career rates, and the "completed" events list starts with the next upcoming event.
- Options considered:
  1. Parse straight into database rows (normalize method, weight class, gender inside the parser).
  2. Parsers return what the page says in the site's vocabulary as typed pydantic models; a separate step maps it to our vocabulary using the Phase 1a functions.
  3. Regex over the raw HTML, no HTML library.
  For the HTML library: BeautifulSoup with lxml, BeautifulSoup with the built-in `html.parser`, or selectolax.
- Decision: option 2, with BeautifulSoup + lxml. Parsers are pure (`parse_*(html, url) -> model`, no network, no database, no logging); the URL is a plain argument because event and fight pages don't contain their own id. Mapping to `decision`/`unanimous`, canonical weight class and gender happens in checkpoint 3 with `normalize_result` and `fight_weight_class`, so scraped and seeded rows go through the same code. BeautifulSoup keeps document order on the malformed per-round table (tested with both backends), so that table is read in order ("Round 1", row, "Round 2", row, ...) rather than by nesting; lxml because the warm-cache benchmark re-parses every page and is CPU-bound (measured in checkpoint 5), and it ships wheels. selectolax's default backend is deprecated and failed to import. Rules baked into the models: a blank cell ("--", "---", empty) is None and a published "0 of 0" stays 0; an unknown value format raises instead of guessing; the fight model has no date field (the event page is the only source of a fight's date); the fighter model has exactly four bio fields and no career rates or record (a test pins the field list); event-page fighter order is documented as winner-first and never used as a corner or a column order, and only the fight page (first fighter, confirmed against the seed's red corner in 6 of 6 fixtures) can supply the red corner. Layout checks are deliberately loose: required landmarks must exist and each table must have the expected column count plus a few key headers (lowercased, punctuation removed, "contains" tests at fixed positions), and cells are read by position, so a cosmetic fix on the site (the "Td %" typo, capitalization, punctuation) changes nothing, while a removed column or missing landmark raises `ParseError` (permanent, never retried, goes to the DLQ with the URL). Suspicious values that don't make a page unreadable (per-round significant strikes not adding up to the total, an unrecognized time format) are returned in `anomalies` on the model; `report_anomalies()` logs a WARNING and counts `scraper_parse_anomaly_total{source,kind}`, called by the jobs, so the parser stays pure and the page still loads.
- Tradeoff: a markup change that keeps the column count and the checked headers but reorders other columns would parse wrong values, not fail; the per-round sum check and the cross-check between the event page's winner and the fight page's W/L badge (a test now, an ingestion check in checkpoint 3) are the backstops. Only a few headers are checked, so some cosmetic fixes pass and some real changes slip through. Mapping to our vocabulary lives in a second step, so there are two places to look when a value is wrong. Revisit if a parse anomaly shows up in production often (tighten the checks), or if parsing speed matters at scale (the warm benchmark will say).

### D-019: Upserts: two column policies, three-way counts, and what happens on conflict
- Context: every ingestion job writes into the Phase 1a tables, and must be safe to run twice. The scraped rows also overlap the seed (the same fights), so a rerun, a replay and a first scrape over seeded data all hit existing rows. We also need honest numbers for "a rerun inserts nothing new" and the benchmark.
- Options considered:
  1. Insert-or-replace the whole row every time.
  2. `ON CONFLICT DO UPDATE` setting every column to the new value.
  3. `ON CONFLICT DO UPDATE` with a policy per column, and a `WHERE` clause so an unchanged row isn't written.
- Decision: option 3, keyed on ufcstats ids. **Result columns** (`outcome`, `winner_id`, `method`, `decision_type`, `method_detail`, `finish_round`, `finish_time_sec`) are replaced as a unit by the latest fight page, NULLs included: a NULL winner is a real value (a no contest), so an overturned win must be able to clear its winner (see D-015's amendment). **Everything else** (bio, stats, referee, weight class, scheduled rounds, gender) is monotonic fill: a new non-NULL value overwrites, a new NULL never erases what we hold, and `has_round_stats` never goes from true to false. Every statement writes only if something would change, so an identical rerun writes nothing (a test checks the row versions' `xmin` don't move), and `RETURNING (xmax = 0)` classifies each row as inserted, updated or unchanged; counts go into a per-run Redis hash (`HINCRBY`, atomic across worker processes). A scheduled bout can never overwrite a completed fight (`WHERE status <> 'completed'`). Stat rows that are no longer on the page are deleted, but a page with no stats never deletes what we hold. A guessed gender (catch weight, open weight) never overwrites a known one. When an update changes a completed fight's result, the store reports a `result_changed` anomaly: scraping over the seed reports exactly two, the two documented differences.
- Scrape vs seed, verified on the six fixture fights (a test pins it, `test_seed_match.py`): every column of every fight, event, fighter and stat row is identical except six values: Vologdin vs Castaneda `outcome` (seed `unknown`, page `draw`), Santos vs Marscucci `finish_time_sec` (seed 27, page 627: 10:27 in a "1 Rnd + OT" fight, probably a seed parse of "0:27"), and Marwan Rahiki's height, reach, DOB and stance (NULL in the seed, since published by the site). The page wins in all three cases: it is the primary source.
- Tradeoff: outside the result group, a field the site later blanks can never be "un-filled" here; revisit if that matters. `xmax = 0` is a Postgres implementation detail for "this row version was created by an INSERT"; it is widely used and a test pins it on Postgres 16. One more Postgres detail that bit us: NOT NULL is checked on the proposed insert row before the conflict is detected, so "keep the existing value" can't be expressed by passing NULL for a NOT NULL column; we pass the existing value instead.

### D-020: Retries, backoff, and the dead-letter queue
- Context: jobs fail for different reasons. A timeout or a 503 may pass on its own; a 404 or a page we can't parse never will; a bot challenge means the site said no. Retrying the second and third kinds wastes requests (and, for a block, goes against D-013). Failed-for-good jobs need a place a person can inspect and replay.
- Options considered:
  1. RQ's default: retry every failure N times at a fixed interval.
  2. Our own retry loop inside the job wrapper, re-enqueueing with `enqueue_in`.
  3. RQ's `Retry` with a per-job jittered schedule we compute, plus a classifier that zeroes the retries for errors that can't improve. For the DLQ: RQ's `FailedJobRegistry`, or our own Postgres table.
- Decision: option 3. Classifier (`policy.py`): timeouts, 5xx, 429 and transient database or Redis errors retry; 404 and other 4xx, parse and mapping errors, robots problems, a missing prerequisite and `SourceBlocked` do not; anything unrecognised is a bug and does not retry either, so it reaches the DLQ quickly with its traceback instead of being repeated five times. A permanent error sets the running job's `retries_left = 0` and re-raises; with `SimpleWorker` that sends it straight to the failed registry (tested). Schedule: 5 retries, "equal jitter" (a random delay in [d/2, d]) on d = 30, 60, 120, 240, 480 s capped at 900, computed per job at enqueue time because RQ takes a plain list of seconds; jitter keeps workers that failed together from retrying together. All of it is env-configurable (`INGEST_RETRY_BASE_S` and so on; tests use base 0). **The DLQ is RQ's `FailedJobRegistry`, which is good enough as the store**: it already keeps the function, arguments, traceback and our `meta` (reason, last reason, error class, attempts, url, run id, failed_at), and RQ can re-enqueue it; a Postgres table would duplicate that. Its weaknesses and our answers: entries expire after a year by default (we set `failure_ttl=-1`); it lives in Redis, which is volatile (compose uses AOF, production needs `maxmemory-policy noeviction`, Phase 2c and 6); it can't be queried by reason (the DLQ is small, so we scan; `meta` carries the reason); and RQ's own `requeue` keeps `retries_left = 0`, so a replayed job would never retry. So replay deletes the failed entry and its claim and enqueues a fresh job with a fresh retry budget, and puts the dead letter back if that enqueue fails. Each dead-lettering is also a structured log line with the job id and url, which is the audit trail after a replay or purge.
- Tradeoff: a dead letter's history disappears from Redis once replayed (the log line is what remains). Classifying every unknown error as "don't retry" means a transient bug in our own code goes to the DLQ instead of quietly passing; we prefer to see it. Revisit if the DLQ needs reporting beyond a scan (a Postgres mirror), or if reasons need to be queryable at scale.

### D-021: Dedupe with claim keys (RQ does not dedupe job ids)
- Context: many fights point at the same fighter, so a backfill would enqueue "fetch fighter X" dozens of times. The obvious fix, a deterministic job id from the URL, doesn't work by itself: we tested RQ 2.12 and enqueueing the same id twice puts it on the queue twice. RQ also only accepts letters, numbers, underscores and dashes in an id, so the ids are `fighter-<id>`, `fight-<id>`, `event-<id>`, `discover-completed-p<N>-since-<date>` and `discover-upcoming`.
- Options considered:
  1. Check whether a job with that id exists, then enqueue (a race: two workers check at the same instant, both see "no", both enqueue).
  2. A per-run set of enqueued ids (`SADD` returns whether it was new).
  3. An atomic claim per job id, `SET ingest:claim:<job_id> <run_id> NX EX <ttl>`: Redis puts the card down for the first caller only, in one step.
- Decision: option 3. The claim is taken before enqueueing and released if the enqueue fails; deleted when the job succeeds (so a later run can enqueue the id again, and `result_ttl=0` deletes the finished job too); kept with no expiry when the job is dead-lettered (so a rerun doesn't pile onto it; replay and purge clear it). Eight workers enqueueing the same fighter 10 times each produce exactly one job (a test). Dedupe is an optimisation, not what keeps the data correct: a duplicate that slips through hits the fetcher cache and the idempotent upserts (D-019), so it is harmless.
- **Known limit: the claim's expiry (`INGEST_CLAIM_TTL_S`, default 2 hours) is shorter than a full-history backfill.** The seed alone is 774 events + 8,555 fights + 2,686 fighters, about 12,000 pages, roughly 3.3 hours at 1 request/second. A job that waits in the queue past 2 hours loses its claim, and a later enqueue of the same id is accepted. That costs one extra queue entry that does no network work (cache hit) and writes nothing (unchanged upsert): wasteful, not wrong. The 12-month benchmark (about 1,200 pages, roughly 20 minutes at 1 request/second) stays well inside the window. If it ever mattered: (a) raise `INGEST_CLAIM_TTL_S` above the expected run length (one env var; the cost is that a crashed worker blocks its id for longer); (b) refresh a claim's TTL whenever the same id is enqueued again; (c) replace the TTL with a lease the running job renews; or (d) dedupe per run, with a set of enqueued ids that lives as long as the run. We start with (a).
- Tradeoff: a worker that crashes mid-job leaves its claim until the expiry (RQ's own recovery re-runs the job, so the work isn't lost); every enqueue costs one Redis round trip.

### D-022: `SimpleWorker`, and Linux/macOS only
- Context: RQ's default worker forks a new process for every job. Prometheus counters incremented inside that child (our cache hit, fetch latency and limiter wait metrics, and the job metrics) vanish when it exits, so `/metrics` would show zeros. RQ's job timeouts use `signal.SIGALRM`.
- Options considered:
  1. Keep the forking worker and add Prometheus multiprocess mode (files in a shared directory).
  2. Keep the forking worker and count in the parent process only (loses the fetcher's metrics).
  3. `SimpleWorker`, which runs each job in the worker's own process.
- Decision: option 3, with `job_timeout=300` and `max_jobs` so a worker exits and is restarted periodically (Kubernetes does that in Phase 6). We scale by running more worker processes, which is what the Phase 1b benchmark measures. We tested that a 5-second job with a 1-second timeout is stopped after 1.0 s by `SIGALRM` under `SimpleWorker` and lands in the failed registry (and a test pins it). **Platform support: Linux and macOS only.** RQ's package metadata lists only POSIX, Unix and macOS, and `SIGALRM` does not exist on Windows, so on native Windows every job would fail the moment it started; RQ's thread-based `TimerDeathPenalty` can't interrupt a blocking call, so we don't rely on it (this part is from RQ's metadata and the signal API, not a run on Windows). The dev machine is WSL2 Ubuntu, production is Docker/k3s: both are Linux. `ensure_supported_platform()` makes the worker refuse to start on `win32` with a message to use WSL2 or Docker. The scraper's fetcher and parsers are plain Python and are not affected.
- Tradeoff: no process isolation, so a memory leak accumulates until the next restart and a hung job depends on the signal timeout; the fetcher's `httpx` timeout bounds the network side. Revisit if jobs ever do CPU-heavy work (Phase 4 embeddings), where a forking or spawning worker earns its cost.

### D-023: Fight status lifecycle and a NULL outcome for unfought bouts
- Context: `fights` assumed every row had already happened. The live scraper also sees upcoming bouts, and bouts that get removed from a card. An upsert only adds or updates, so a removed bout would stay behind as a phantom, and Phase 5 would grade a prediction for a fight that never happened.
- Options considered:
  1. A separate `scheduled_fights` table (a parallel schema).
  2. A `status` column on `fights`, with unfought bouts using outcome `'unknown'`.
  3. A `status` column, with a NULL outcome, method and title flag for unfought bouts.
- Decision: option 3 (migration 0006). `fights.status` is `scheduled`, `completed` or `cancelled` (default `completed`, so all 8,555 seed rows stay valid). `outcome`, `method` and `is_title_fight` become nullable: a bout with no result has no outcome (NULL), and `'unknown'` keeps meaning only "a completed fight whose result the seed couldn't determine" (2 rows). The event page doesn't say whether a bout is a title fight or how many rounds, so those stay NULL rather than a made-up false; `red_fighter_id` stays NULL until the fight page gives it (the upcoming card's order isn't verified as corner order). **The NULL gotcha:** a SQL CHECK passes when its condition evaluates to NULL, so the old `win_has_winner` (`(outcome = 'win') = (winner_id IS NOT NULL)`) is NULL for a bout with no outcome. It is rewritten NULL-safe (`IS NOT DISTINCT FROM`), and two explicit CHECKs are added: a completed fight must have outcome, method and title flag, and an unfought bout must have none of them (a scheduled row with a winner is rejected by both `win_has_winner` and `unfought_has_no_result`). `completed_fights` (a view) is the one door for the feature pipeline and grading; `fight_pre_rankings` reads `fights` directly, so it also covers scheduled bouts, which Phase 2b needs. Transitions: a bout with no result on its event page is upserted `scheduled`; when its result appears the fight job makes it `completed`; a completed fight never goes back; on every event refetch a scheduled bout that is absent from the page becomes `cancelled` (never deleted, so a stored prediction stays explainable) and a cancelled bout that reappears is scheduled again; a 404 on a known event cancels its scheduled bouts. Guards: a page that lists no bouts while we hold scheduled ones cancels nothing and is reported; an event that falls off the upcoming list is re-checked with a forced refetch, never assumed cancelled; a completed fight missing from its event page is flagged but untouched; scheduled bouts more than 7 days past their event are flagged as stale.
- Tradeoff: queries like `WHERE outcome <> 'draw'` silently drop NULL rows and `GROUP BY outcome` shows a NULL group: right for unfought bouts but easy to do by accident, which is why training and grading read `completed_fights`. A women's catch-weight bout would be stored with gender `M` (the weight class doesn't say), recorded as a `gender_assumed` anomaly and never allowed to overwrite a known gender. The downgrade refuses while any scheduled or cancelled fight exists. Revisit if an upcoming fight page turns out to carry the title flag and round format (then scheduled bouts could carry them).

### D-024: The worker process: liveness from a heartbeat, hold instead of exit, one small CLI
- Context: checkpoint 4 turns the pipeline into something you operate: a command line, a worker process Kubernetes can run, and `/healthz` and `/metrics`. Two questions have real consequences. What should make a worker look dead to Kubernetes (a failed liveness probe restarts it)? And what should a worker do when the site blocks us (D-013)?
- Options considered:
  1. Liveness: (a) the process answers HTTP; (b) a dependency check, 503 when Redis or Postgres is unreachable; (c) a heartbeat from the worker's own loop, 503 only when it goes stale.
  2. When the breaker is open: (a) the worker exits with a distinct code (3); (b) it carries on dequeuing, so every queued job fails fast and lands in the dead-letter queue; (c) it holds: stays up, takes no jobs, re-checks the breaker every 30 s.
  3. Tooling: `typer`/`click` and FastAPI versus `argparse` and the standard library's `http.server`.
- Decision:
  1. **(c), a heartbeat.** The worker stamps a local timestamp every time its loop looks at the queue or finishes a job (it overrides RQ's `heartbeat()` and stamps *before* RQ writes to Redis, so it still ticks if Redis is down). `/healthz` is 200 while the pulse is younger than `INGEST_JOB_TIMEOUT_S + WORKER_HEALTH_MARGIN_S` (300 + 60 s) and 503 after, which catches a wedged loop or a job stuck where RQ's timeout can't interrupt it. Redis, Postgres, the breaker, queue depth and dead-letter count appear only in the JSON body and in `/metrics`, never in the status code. Why not (b): a Redis blip would restart every worker at the same moment, and a restart doesn't fix Redis. Details that make the pulse reliable: the worker is built with `worker_ttl=30`, so an idle worker wakes every 15 s (RQ's default is 405 s); RQ retries a dead Redis with waits of up to 60 s, which keeps the loop, and so the pulse, ticking through an outage; and if `work()` ever returns unexpectedly (a Redis timeout, an RQ error) the runner builds a new worker in place instead of exiting. **The HTTP handler does no I/O:** RQ gives the worker's Redis connection a 25 s socket timeout, so a health request that used it could hang through an outage, and a probe timeout counts as a failure. A background thread takes a snapshot every 10 s with its own Redis and Postgres clients (2 s timeouts, no retries) and requests only read the latest one; the body shows the snapshot's age. `/metrics` reads the same snapshot, so queue depth, `ingest_dead_letters_current{reason}` and `scraper_breaker_open{source}` are at most one interval old, and a value that couldn't be read is left out rather than reported as zero. (The plan said gauges would read Redis at scrape time; the snapshot keeps scrapes from blocking too.)
  2. **(c), hold.** A Deployment restarts a container however it exits, so (a) would crash-loop and re-fetch robots.txt on every restart, while only a person can clear the breaker. And (b) would drain the whole queue into the dead-letter queue within minutes. So the worker checks the breaker before every dequeue (one Redis GET); while it is open the worker takes no jobs, keeps its pulse, sets `ingest_worker_hold{reason}` and `scraper_breaker_open`, and polls every `WORKER_HOLD_POLL_S` (30) until it is reset, then re-runs the start-up preflight (robots.txt) and resumes. When the site starts blocking us at most one in-flight job per worker dead-letters (reason `source_blocked`, replayable); the rest of the queue stays queued. I extended the same hold to robots.txt problems (disallowed, unreachable) because the same restart-loop reasoning applies. **Exit codes matter for one-shot callers (the CLI, scripts, CronJobs), not for Deployments:** `backfill` and `dlq replay` exit 3 while the breaker is open, and `worker --burst` (one-shot by definition) exits 3 and leaves the queue untouched. The long-running `worker` never exits for these reasons.
  3. `argparse` plus the standard library's `http.server` in a daemon thread: no new dependency, and about a dozen commands don't need more. `prometheus_client`'s own server only serves `/metrics`; we also need `/healthz`. The server binds `127.0.0.1` unless `WORKER_HTTP_HOST` says otherwise (containers set `0.0.0.0`).
- Found by running the real process, not the unit tests (both fixed, both have tests): after SIGTERM an *idle* worker was restarted by the runner as if it had crashed, because RQ sets `_stop_requested` only when a job is running (an idle worker gets an exception, and only `_shutdown_requested_date` records it); and the saved pages link to `http://ufcstats.com/...`, which a source with a different base URL correctly rejects, so the stand-in (and later the replay server) rewrites links to its own address. The HTTP and observer threads start only after RQ has forked its scheduler, so the child process never inherits them; RQ's own pub/sub thread already exists at that point, so Python still prints its "fork in a multi-threaded process" DeprecationWarning (RQ's design; the child only runs RQ's scheduler loop, but it is a known fork-and-threads hazard to remember when upgrading RQ or Python).
- Tradeoff: a heartbeat can't see a worker that is alive but useless (for example failing every job because Postgres is down); that shows up in `ingest_jobs_total{outcome="dead_letter"}`, `ingest_dead_letters_current` and `/healthz`'s body, so Phase 6 needs alerts on those. A wedged worker takes up to 6 minutes to be replaced. Holding makes a block fail *quietly*: the pods look healthy, so **Phase 6 must alert on `scraper_breaker_open == 1`**, or a block could go unnoticed. A reset takes up to 30 s to be noticed. The dead-letter gauge reads every failed job on each refresh, fine while the dead-letter queue is small (hundreds), not at tens of thousands. There is no readiness or startup probe yet (Phase 6). `breaker reset --yes` is a deliberate footgun with one guard (`--yes` and a WARNING log): someone can clear it without reading what the site said. Revisit the tooling if the CLI passes about 15 commands, and the liveness design when Kubernetes arrives in Phase 6.

### D-026: Benchmarking ingestion against a synthetic replay corpus, and keeping the relaxed rate limit off the real site
- Context: the brief asks for a 12-month backfill benchmark, 1 worker versus 4, cold and warm cache, and an explanation of why 4 workers isn't 4x. ufcstats.com is behind a bot challenge (D-013), and we hold 14 real pages, while a year of events is about 680 pages. Running the benchmark against the real site is impossible, and running it at the real site's 1 request/second would take 11 minutes per run and could never show anything but the limiter.
- Options considered:
  1. Replay the 14 saved pages over and over. Cheap, but it isn't 12 months of events (the same ids would collide and the idempotent upserts would make most of the work vanish).
  2. Mock the HTTP client inside one process. Fast, but it removes the real processes, the real queue and the real network round trip, which are exactly what a worker-scaling benchmark measures.
  3. A replay server that serves a **generated** year of events, cloned from the real fixtures, at a latency we choose, with real worker processes, Postgres and Redis around it.
- Decision: option 3 (`scripts/replay_corpus.py`, `scripts/standin_site.py`, `scripts/bench_ingest.py`). One synthetic event is a copy of the Burns card cut down to the 4 bouts we hold full fight pages for: 1 event page + 4 fight pages + 8 fighter pages. 52 weekly events end up as about 680 requests per cold run. Every id in a page URL is mapped to `sha1(id|k)[:16]` consistently across the event's pages, pages are rendered on request, and the same arguments give byte-identical pages. The server answers after a seeded `250 ms +/- 20%` delay and is threaded, so concurrent requests overlap like a real site's. **The 250 ms is an assumption** (a typical US-hosted small-site round trip, 100-400 ms); no real latency exists to measure because every page ufcstats ever gave us was the challenge page. A latency sensitivity series (100 and 500 ms) bounds how much the guess matters, and a measured latency replaces it as soon as access is real. The benchmark runs as a matrix (D4 in the plan: the limiter at 1000 ms as we would run it live, at 100 ms to expose the worker-bound region, latency sensitivity, warm cache, and a rerun on a full database), each run in a fresh `cageops_bench` database and Redis database 2. Every run is **validated**: no dead letters, the exact expected row counts, the exact expected number of requests (cold) or zero (warm and rerun); a run that doesn't add up is recorded as invalid with the reasons. The predictions were committed to BENCHMARKS.md before the first run.
  **The relaxed limiter can only ever apply to the replay source.** Series B and C use a 100 ms interval, which is acceptable only because they never touch the real site. While planning I found that the 1000 ms floor was keyed on the source *name*, so `SCRAPER_SOURCE=ufcstats_replay` with a replay URL of `http://ufcstats.com` would have run at 100 ms against the real site. Three layers now close that: `ScraperSettings` rejects any replay base URL that is not loopback (and any interval under 1000 ms for source `ufcstats`), the harness refuses a relaxed interval for any other source and always sets `SCRAPER_SOURCE=ufcstats_replay` for its workers, and `build_context()` (every worker and CLI command) fails on a bad configuration. The harness also refuses to reset anything but the `cageops_bench` database and Redis database 2.
- Found while building it (each fixed, each tested): the run statistics counted fighters only as `updated` (the bio write), because the name-only rows a fight or event job creates were never counted, so an "inserted versus updated" table would have been wrong; the page cache is keyed by URL, so the replay server needs the same port on a cold and a warm run or the warm run misses its own cache; the "next event" marker row on the events list must be dated far in the future, or a backfill run after that date fetches it as a completed event; and **workers must be long-running, not `--burst`**: a burst worker exits as soon as the queue is empty, and at the start the queue holds one discovery job, so 3 of 4 workers would quit at once and a "4 worker" run would silently be a 1-worker run.
- Tradeoff: the corpus proves the plumbing and shows where the bottleneck is; it says nothing about the real site's latency, data volume per event, fighter overlap between cards (real cards reuse fighters, so real runs have more cache hits and fewer fighter pages per fight) or markup quirks. The workers, the replay server, Postgres and Redis share one machine, so CPU and disk contention can flatten the warm-cache scaling. The 250 ms stays a guess until a real run measures it. The relaxed limiter is guarded by code rather than by trust, but the loopback rule would need loosening on purpose if someone later runs the replay server on another machine. Revisit when ufcstats access is real: re-run the 12-month backfill against the live site (1 worker, 1 request/second) and compare.

### D-027: Point-in-time features: what "before" means, and what we do when we can't tell
- Context: Phase 1c builds `fight_features`, one row per (fight, fighter). The model must only see what was knowable before the fight (CLAUDE.md rule 1). Doing that needs a dozen small rules (what counts as history, how to measure a fight's length, what to do with draws and gaps), and each one is a place a future leak or a silent wrong number can hide.
- Options considered:
  1. Compute in SQL window functions (`ROWS BETWEEN UNBOUNDED PRECEDING AND 1 PRECEDING`).
  2. A dataframe library (pandas/polars) with rolling windows and a `shift()`.
  3. A pure Python function that is handed only the fighter's prior fights, with the date filter in one other function.
- Decision: option 3 (`cageops_worker/features/`, migration 0007). `history.prior_fights` is the only place dates decide what history is, and `compute.compute_features` never sees a date it could misuse. Plain Python needs no dependency (`uv.lock` is unchanged), and the leakage tests can call the function without a database. Rules:
  - **Strictly before.** History = the fighter's `completed` fights with `event_date < the fight's date`, same as `fight_pre_rankings`. A fight on the same date is not history.
  - **Ordering.** History is sorted by `(event_date, fight_id)`, so the last-3/last-5 windows and the win streak are identical across rebuilds. Within one date the order is arbitrary but stable (it is the fight id, not the real bout order). It only matters to a later fight whose history holds several same-date fights; same-date fights never see each other.
  - **Rates are a ratio of sums** over the window (total landed over total minutes), never a mean of per-fight rates, so a 20-second knockout doesn't dominate. Windows are career, last 3 and last 5 prior fights (stats-less fights still count toward the window size).
  - **Any zero denominator is NULL**, never 0: opponent attempts 0 for `sig_str_def` and `td_def`, own attempts 0 for `sig_str_acc`, total minutes 0 for the per-minute and per-15 rates. A fight with no stats, or with no trusted duration, is left out of that rate's sums. A real zero (0 landed of 10 attempted) stays 0.
  - **Takedown defense is a ratio, deliberately.** ROADMAP 1c says "takedowns landed and defended per 15 min"; `td_def` is instead 1 minus the opponent's landed over the opponent's attempted, and there is no `td_defended_per15`. A per-15 count of defended takedowns mostly reflects how often opponents attempt takedowns (their style), not how well the fighter defends them, and Phase 2 already gets opponent takedown volume from the opponent's own `td_landed_per15` in the A-B differences.
  - **Fight length.** The DB stores only `scheduled_rounds`; the real time-format string ("3 Rnd (5-5-5)") is parsed by the scraper but not kept, and the silver seed never had it. So we trust only `scheduled_rounds` of 3 or 5 (rounds of 300 s) and a consistent finish (`1 <= finish_round <= scheduled`, `1 <= finish_time_sec <= 300`, and a decision must run `finish_round == scheduled` and `finish_time_sec == 300`). Everything else gets a NULL duration: out of the time-based rates, still counted in the window's `n_fights`. In the 8,555 seed fights that is 220: 209 non-standard formats (31 with no round count, 167 one-round, 11 two-round) and 11 decisions in 3/5-round fights that stop short. The 11 look like technical decisions after an accidental foul (the time may well be right, e.g. 2:18), so NULL is the conservative side. These counts are the `completed_fights_with_null_duration` fields (`total`, `format_not_standard`, `decision_not_full_length`) of the report printed by `uv run python -m cageops_worker.features rebuild`, run on 2026-10-06 against the seed-only database. They are a snapshot and will change as more results are ingested. A `time_format` column (scraper stores `time_format_raw`) would only help scraped fights (none real yet), because no seed source carries the string.
  - **Win streak.** Walk back from the latest fight: win +1; loss or draw stops; no contest is skipped (neither extends nor ends it); an unknown result that the walk reaches makes the streak NULL (one behind a loss or draw doesn't matter). No prior fights is 0. `finish_rate` = finishing wins (KO/TKO, submission) over fights with a decided result (win or loss).
  - **`prior_ufc_fights`, not `total_fights`.** It counts UFC fights in our DB strictly before this one: *prior* (point-in-time safe) and *our DB only*. The ufcstats all-pro record is not used, because it is a scrape-time snapshot (the same leak as the silver `SlpM`/`Str_Acc` columns, D-008).
  - **Results gap.** Scheduled fights dated today or later are built (Phase 2 predicts them). A `scheduled` fight dated before the build's `--today` never got a result: it is neither history nor an upcoming bout, so it is **excluded and reported** (count, ids, dates). Each row whose fighter has such a fight before the row's own date gets `has_unresolved_prior_fight = true`. A fight date can't be flagged when the event was never scraped at all (events from 2026-05-17 until Phase 1d are simply absent); the report's `history_through` states how far our history reaches. In the seed-only database there are 0 past-dated scheduled rows and `history_through` is 2026-05-16.
  - **Bio.** Height, reach and stance are one scrape-time value per fighter. Age is safe (a birth date doesn't change). The tiny risk that a fighter's listed reach or stance changed is accepted and documented. `is_title_fight` and `scheduled_rounds` of the fight being featured are pre-fight facts, but they are NULL for upcoming bouts (D-023) and filled for completed ones, so Phase 2 should expect that train/serve difference.
  - **Rebuild.** `features rebuild` recomputes everything in one transaction (delete and re-insert, like the rankings load), and aborts and rolls back unless every target fight produced exactly two rows. Foreign keys tie rows to `fights`, `fighters` and `load_runs`. `load_runs.sha256` holds a hash of the output rows, so two builds from the same data are comparable with one string.
- Found while building it: the existing loaders (silver, odds, rankings) write their `load_runs` row inside the same transaction as the load, so **a failed run rolls its own record back and leaves no trace in `load_runs`**; the only trace is the exit code and stderr. The feature rebuild follows the same pattern on purpose (the old table survives a failure, and the CLI prints `ERROR:` and exits 1). Whether failed loads should be recorded is a separate decision that would touch every loader.
- Tradeoff: **a rebuild uses current results, so if a result is overturned later (a win becoming a no contest, D-015), fights that happened between the original result and the overturn are built with the corrected history, not with what was known at the time.** A true as-of rebuild would need result history, which we don't store; it matters for honest backtests of those few fights, not for the shape of the pipeline. Also given up: a fighter's real bout order within a date; rates for the 220 fights with no trusted length; and speed (a Python loop over about 17,000 rows; not benchmarked, so no number is claimed). Revisit when the table is large enough that a rebuild hurts (Phase 5 would move to incremental updates), or when a real time-format column exists.
- Amended by D-033 (2026-10-14): the build's report (and `load_runs.report`) now also carries `inputs_sha256`, a hash of what the build read (completed fights, their dates, bios and whole-fight stats), so the trainer can tell whether the features are stale. `output_sha256` is unchanged: a rebuild after the change produced the same `5b23d187...` as the build before it. `history.py` exposes its read set as tuples so a test can check the hash covers it.
- Amended by D-037 (2026-10-15): `age_days` and `days_since_last_fight` are now derived by `cageops_common.inference.asof.date_relative_features`, which `compute_features` calls instead of its two inline expressions; a read-only recompute of the real build reproduced `output_sha256` `5b23d187...` exactly. `features rebuild --today` now defaults to today in `APP_TIMEZONE` (America/New_York), not the host's local date. The build also writes `fighter_features_current` in the same transaction.

### D-028: A second results source: English Wikipedia article pages, not its API
- Context: ufcstats.com is behind a bot challenge we won't bypass (D-013, D-025), and our seed ends 2026-05-16. 1d needs a results source that permits automated access, to close the gap (18 events by 2026-10-03) and give Phase 5 results to grade against. Checked on 2026-10-06 (the full log is in DATA_SOURCES.md section 6): Wikipedia's robots.txt disallows `/w/` (which covers `/w/api.php`) and `/api/` for generic agents and has no Crawl-delay; plain `/wiki/<Title>` pages are allowed. Wikimedia's policy calls the API the intended bot channel (1 concurrent request, 5 requests/second unauthenticated; "if a request takes more than 1 second to serve, wait 5 seconds"), requires a User-Agent that names the client and a contact, and licenses the text CC BY-SA 4.0 (credit by article URL).
- Options considered:
  1. The Action API (`/w/api.php`), structured and sanctioned for bots, against robots.txt: needs a deliberate exception to rule 2.
  2. Article HTML under `/wiki/`, which robots.txt allows.
  3. A paid data API (Sportradar, UFCalendar and similar): licence and cost, and not "free and permitted".
  4. Wait for ufcstats, or get past its challenge: ruled out by D-013 and D-025.
- Decision: option 2. `WikipediaSource.canonical_url` makes anything else impossible (no `/w/`, no `/api/`, no query string, no `Special:` or other non-article namespace), with a test per forbidden shape, so the API cannot be hit by accident. One request per event article (an article holds every bout), plus one `{year} in UFC` list page per year. Cache: event articles are refetched after 24 hours until 30 days after the event, then final, so a vandalised revision is corrected within a day for a month (older edits need `--force`); year lists 6 hours; a 404 one day. The Robot policy's pause is **implemented**, as a per-source rule: after a live response that took over 1 second the fetcher pushes the next rate-limit slot out by 5 seconds for every worker of that source (`SlowResponse`, `RateLimiter.penalize`, tested with a fake timer; ufcstats has no such rule and is unaffected). The policy writes it for the Action API; we apply it to article pages because it costs almost nothing.
- Tradeoff: HTML tables instead of structured data, so a layout change breaks the parser loudly (loose checks, a `ParseError` into the dead-letter queue with the URL) instead of silently. Wikipedia is edited by anyone: a result can lag or be wrong for a while (D-029). The text is CC BY-SA 4.0, so the cached HTML and committed fixtures carry that licence. 26 requests produced the whole gap, so the cost to Wikimedia is small, and the 1 request/second limiter is far inside every limit in their policy. Revisit if Wikimedia changes robots.txt, or if a permitted ufcstats channel appears.

### D-029: Wikipedia rows in the shared tables: keys, precedence, and holding names that look like old fighters
- Context: Wikipedia gives results only. Its fighters, events and fights may also exist from ufcstats (the seed, or a later backfill), and its text is editable by anyone. We needed identity that survives edits, a rule for who wins when both sources speak, and no splitting of a fighter's history by a spelling difference.
- Options considered:
  1. Made-up ids (`wp:...`) in `ufcstats_id`.
  2. One neutral `source_key` column.
  3. Per-source key columns, with `ufcstats_id` nullable and holding only real ufcstats ids.
- Decision: option 3 (migration 0008). A `wp:` id in a column named `ufcstats_id` is a lie every reader must remember to skip, and the one place that builds a URL from it (the upcoming-events re-check in `jobs.py`) would have requested `/event-details/wp:...` from ufcstats. One neutral key cannot describe a row known to two sources, which per-field precedence needs. So: `ufcstats_id` is nullable on events, fighters and fights and a CHECK (`^[0-9a-f]{16}$`) makes a made-up id impossible; Wikipedia identity lives in `events.wikipedia_article_id` (the article's `wgArticleId`, which survives a rename) and `fighters.wikipedia_title` (the link target, which survives a display-name edit); a fight needs no source key because `UNIQUE (event_id, fighter_a_id, fighter_b_id)` is its identity. `fights.result_source` (`ufcstats` or `wikipedia`, set exactly when a fight has a result) says whose result a fight carries. Every reader of `ufcstats_id` that builds a dict or a URL got `IS NOT NULL`: the upcoming-events re-check in `jobs.py` (the only path from a stored id to a URL), the event reconcile in `store.py`, the seed id maps (`silver.py`, `resolver.py`, `odds.py`). The `jobs.py`, `store.py` and `silver.py` ones have a test that fails without the filter; the `resolver.py` and `odds.py` ones are defensive (a NULL key in a dict is harmless there) and have smoke tests only. The other places that touch ids read them from pages or file names, never from a stored row.
  - **Precedence, per field.** A ufcstats result is never replaced (a disagreement is only reported: `source_disagreement`). A scheduled ufcstats bout with no result is filled in and keeps its ids. A Wikipedia result is updated, with `result_changed` (Phase 5 re-grades on it). A cancelled ufcstats bout is reported and left alone. ufcstats results always replace Wikipedia ones: `write_completed_fight` now sets `result_source = 'ufcstats'`. A ufcstats scheduled bout that Wikipedia does not list is reported and never cancelled; this writer never calls the ufcstats scheduling functions. The write is also guarded in SQL (`only_if`), tested directly.
  - **Matching.** An existing fight with the same unordered fighter pair within one day of the article date is the same fight, and its event is the article's event (a date alone can't identify an event: 5 dates in the seed have two). Else the event is found by article id, else created. An article's bouts matching fights in several events is an error. `event_date_collision` reports a new event created within a day of another.
  - **Names.** A fighter is found by link target, then by the same `NameResolver` the seed uses (with the reviewed `wikipedia` rows of `seed/aliases.csv`, loaded by the writer itself, so editing the file and replaying is the whole workflow). A name that matches nobody exactly is **held for review, with nothing written for that event**, if it looks like an existing fighter: the same words in another order, the same letters spaced differently ("Park Jun-yong" / "JunYong Park"), one typo, a 0.9 similarity, one name's words all in the other ("Michelle Waterson" / "Michelle Waterson-Gomez"), or the same surname and first initial ("Beatriz Mesquita" / "Bia Mesquita"). The message names the link title and the candidates. A person then adds an alias row, or adds the link to `wikipedia_distinct_fighters.csv` with a reason, and replays. Any other unmatched name becomes a stub fighter (name and link only, no bio). Ambiguous names are never guessed.
  - **Facts only.** Names, dates, winner, outcome, method class, decision type, round and time are stored. The method's parenthesis, scorecards and the notes are not (`method_detail` stays NULL): the notes are read once to decide the title flag and dropped. A title fight is a footnote that says a UFC championship (undisputed, interim or vacant); a BMF footnote is not one, matching the seed (UFC 244 is false there); a `(c)` marker with no such footnote is reported, not guessed.
  - **Jobs.** The same queue, claims, retries and DLQ as 1b. An event job's id is its article *title* at enqueue time (the article id isn't known until it is read); the writes are idempotent by article id, so a renamed article is the same event. `scrape-upcoming` is refused for this source.
  - **Features (D-027).** Wikipedia fights have no stats and no `scheduled_rounds`, so they count in `prior_ufc_fights`, `win_streak`, `finish_rate` and `days_since_last_fight` but not in the rates or the duration; stubs have no bio, so age, height and reach are NULL. `history_through` moved to 2026-10-03 and the NULL-duration total rose from 220 to 444. `completed_fights` is `SELECT *` frozen at creation (D-023), so it does not show `result_source`; the features don't need it.
- Found while building it (measured, and the reason for the name rules):
  - Agreement with the seed on five saved cards (UFC 244, 249, 259, 321, 323), 65 bouts, 58 matched by name: **every** outcome, winner, method, decision type, round, title flag and gender is identical. The expected differences are pinned in a test: ufcstats files a catch-weight bout under its nominal division where Wikipedia says catchweight (5 bouts, so Wikipedia rows say "Catch Weight"), and one finish time disagrees (47 s against 40 s, UFC 259).
  - **7 of 65 bouts (11%) had a fighter named differently from the seed's.** On six cards 17 names matched nobody: 7 were old fighters under another spelling (hyphenation, nicknames, an extra surname, a transliteration) and 10 were new. A 0.9 similarity plus a one-typo rule, the first version of the check, flagged none of the 7. The rules above flag 6 and none of the 10 new ones. Not caught: a transliteration ("Alexey Oleynik" / "Aleksei Oleinik") and a name change ("Katlyn Chookagian" / "Katlyn Cerminara").
  - The real gap run (18 events, 224 bouts, every bout checked against the article's own count) was **held by this check**: 14 events stopped on the first pass, 6 after the first review, 2 after the second, none after the third. 21 names were flagged: 18 were existing fighters (18 alias rows, each with its evidence in the note; one, Osman Diaz as Ozzy Diaz, is marked lower certainty) and 3 were new (`wikipedia_distinct_fighters.csv`). Without the check about 18 fighters would have been split, each with a reset history. 74 fighters were created in all: the 3 above and 71 that matched nobody and looked like nobody. The check cannot prove those 71 are all new, so the run's stub list is a review step.
- Tradeoff: every held name needs a person once, and the evidence (same division and era) is judgment, not proof. A name change or a transliteration that no rule sees becomes a duplicate fighter until someone notices in the stub list. **The remaining gap, not built:** when ufcstats access returns, the 1b writers find rows by `ufcstats_id`, so they will not find Wikipedia-created rows (NULL id) and would add duplicates; `result_source` makes replacing a result safe, but merging identities needs an adoption step (match the event by date and fighter pair, a fighter by name or link title, then fill in `ufcstats_id`). Wikipedia results can lag or be vandalised: the 24-hour refetch for 30 days corrects a bad revision within a day, but a vandalised result is accepted at fetch time, so `result_changed` and the Phase 5 weekly refresh stay the safety net, and an edit after day 30 needs `--force`. Licence: stored rows are facts only (no notes, technique text or other prose), so the share-alike question narrows to the raw HTML cache (`raw_pages.html` holds whole CC BY-SA articles) and the committed fixtures, which carry their own NOTICE; settle it before publishing the data (not legal advice). Revisit when the operator answers (D-025), or when the adoption step is needed.

### D-031: Time-based splits: the last 365 days of data are the test, the 365 before are validation
- Context: Phase 2a needs train / validation / test splits, and rule 4 forbids a random split: fighters appear in many fights, and a random split would let the model train on a fighter's later bouts and be graded on earlier ones. Data runs to 2026-10-03. mdabbert odds end 2026-03-28 and the last 223 fights come from Wikipedia with no per-round stats, so the choice of test year decides how many fights the favorite can be compared on.
- Options considered:
  1. Calendar years: validation 2025, test 2026 so far. Easy to say, but 425 test fights and only 114 with odds.
  2. Rolling 365-day windows ending at the last event: test 2025-10-04 to 2026-10-03, validation the year before, train everything older.
  3. Walk-forward (retrain at each of several cut dates and average): the most honest, and several times the work. It belongs with Phase 5's scheduled retraining.
- Decision: option 2. Boundaries are dates, derived from the data (`test_start` = last event date minus one year plus a day, `val_start` a year before that) and overridable; they are stored in the registry row. Train 7,706 fights (1994-03-11 to 2024-09-28), validation 512, test 553 (241 with odds; 330 before 2026-05-17 and 223 from it). Validation is used only to choose the number of boosting rounds; test is scored once at the end. The fighters-in-one-split problem is handled by the date boundary itself, and a test asserts that no training fight is dated on or after the first validation fight, on the dates and not the boundaries. **Baselines and how the comparison is made** (rule 4): the betting favorite uses **mdabbert odds only**, de-vigged by rescaling the two implied probabilities to sum to 1, and only on test fights that have them, with coverage printed as N of M (silver odds are the less-trusted source, D-008, and mixing sources would make the baseline harder to explain; using them as a gap filler is an option if coverage matters later). The experience/ranking heuristic picks the better division rank when both fighters are ranked (the point-in-time `fight_pre_rankings` view), otherwise the fighter with more prior UFC fights; its probability is that pick's win rate on the training split, fit on train only, so it can be scored with log loss and Brier. Model and favorite are always scored on the same fights, with a seeded paired bootstrap on the log-loss gap so a small difference can be told from noise. A coin flip is reported as a reference.
- Tradeoff: the registered model is trained on the training split only, so it has not seen the last two years of fights (its metrics describe exactly that artifact; a refit on train + validation is a Phase 5 job). One test year is 553 fights, 241 with odds, so differences of a few hundredths of log loss are inside noise; a single split also cannot show stability over time, which matters (the heuristic baseline's edge went from 53.8% in training to 41.6% on test). Because the window rolls with the data, versions trained on different days are not scored on the same fights, so their numbers are not directly comparable. Revisit with walk-forward evaluation in Phase 5.

### D-032: What the models learn from and predict: targets, features, order, and a measured omission
- Context: 8,771 completed fights have a decided winner. `fight_features` has 49 columns. Corners are a bias source (the red corner wins 64.19% of fights with a corner; our neutral order, lower fighter id first, wins 50.14%). Two columns, `is_title_fight` and `scheduled_rounds`, are filled for completed fights but NULL for upcoming bouts and for every Wikipedia-sourced fight (D-027, D-029).
- Options considered:
  1. Targets. Win/loss on `outcome = 'win'`, DQ kept or dropped; method as 3 classes (ko_tko, submission, decision) or 4 with `dq`, fight-level or "who wins how".
  2. Fighter order. Train in the stored order; augment with both orders; or one seeded random swap per fight.
  3. Schedule columns: ship them and fill them at serving time, ship them as NULL, or leave them out.
- Decision:
  - **Win/loss** trains on completed fights with a winner. Draws (3), no contests (3) and unknown (2) are out; scheduled and cancelled fights never reach the table the model reads. **A DQ win stays in**: the official result is a real win (24 of 8,771 rows, so either choice is negligible).
  - **Method** is 3 classes, fight-level ("how does this fight end"), and **excludes DQ** (24 fights): a foul outcome that nothing in a striking and grappling feature set can predict, and a fourth class that small only adds noise. `other` only ever occurs with a no contest, which is already out. Per-fighter method odds ("A by KO") are a presentation step for 2b and Phase 3.
  - **Overturned results** have no flag: a refetch replaces the result columns as a unit, so an overturn becomes a no contest and drops out of both models. The weekly forced refresh that would detect one is not scheduled yet (D-019), and `fight_features` is rebuilt with current results (D-027), so a late overturn rewrites history for that fighter's later fights.
  - **Features.** Every `fight_features` column is used or excluded with a stated reason, and a test fails when one is added undecided. 34 numeric columns are used (24 skill rates over career, last 3 and last 5 fights; 3 experience counts; prior UFC fights, win streak, finish rate, days since last fight, age, height, reach), plus stance and weight class. Excluded: identifiers (a model that sees who a fighter is memorizes fighters), build bookkeeping, `has_unresolved_prior_fight`, the 6 `n_fights_with_stats_*` / `n_fights_with_duration_*` counts (they encode era and data source, not skill), and the two schedule columns. Win/loss sees `A - B` for each numeric feature; method sees the mean and the absolute gap, because its target is symmetric in the fighters.
  - **Stance** is a matchup category, not two columns: each stance is normalized to orthodox / southpaw / switch / other / unknown, and the pair becomes `orthodox_vs_southpaw`. For win/loss the string follows the fighter order (the swap reverses it with the negated differences); for method it is sorted, so both orders give one string. Pairs seen fewer than 30 times in training collapse to `other_matchup`; vocabularies come from the training split only.
  - **Order.** One seeded random swap per fight in training (validation too, so early stopping sees no slot). Prediction asks both orders and averages: `p_a = (f(a, b) + 1 - f(b, a)) / 2`, so `P(A) + P(B) = 1` to float precision and swapping the fighters returns the mirror image, whatever the model learned. Both properties have tests; so does the fact that the raw model alone is not symmetric (otherwise the averaging would be dead code). With neutral ids the swap is mostly insurance here, and with corners it would be essential: that is the corner bias (64% red wins) it removes.
  - **Schedule columns are out of the shipped models.** To put a number on that, one extra method model is trained with them and scored on validation only (every validation fight is ufcstats-sourced, so both are filled; never scored on test, never registered, no artifact). Version `20261014-225801`: validation log loss **0.9481 with them against 0.9541 without**, a difference of **-0.0060** over 512 fights. That is the measured cost of leaving them out.
- Found while building it:
  - The experience heuristic's edge reversed: its pick won 53.8% of training fights and 41.6% of test fights. `prior_ufc_fights` is also a model input, so the model may carry some of the same decay.
  - The first report showed only a bare accuracy below 0.5 for it; the report now carries the rule's own pick win rate per split and says so when the edge flips.
  - An empty slice (no test fights from the Wikipedia period in a synthetic league) produced NaN, which Postgres JSONB rejects at the registry insert. Empty slices now report `n: 0`, and the report is dumped with `allow_nan=False` before the insert so a NaN fails with a clear message.
- Tradeoff: no feature selection or tuning, on purpose (this is a systems project). Fight-level method loses "who finishes whom". Leaving two columns out costs about 0.006 log loss on the method model; getting it back needs the follow-up below. Rare stance pairs share one `other_matchup` bucket, so their detail is lost. **Follow-up for 2b and Phase 5:** title fights and main events are known before the fight, so 2b should fill `is_title_fight` and `scheduled_rounds` for upcoming bouts (from the upcoming-event data) and write them into `fight_features` for scheduled fights; they can then return as features in Phase 5. Revisit if the shipped model's validation gain from them grows.

### D-033: Model registry, and not training on stale features
- Context: a version is only worth anything if you can say what it was trained on and reproduce it, and if exactly one is live. Separately, `fight_features` is derived data: if a result is overturned, a bio is filled in, or a Wikipedia replay re-parses cached HTML, a model trained on the old features is quietly wrong.
- Options considered:
  1. Registry as files: a manifest next to each model plus a "current" symlink or file.
  2. A registry service (MLflow): the standard tool, and a new service to run, secure and back up for one table's worth of need.
  3. A Postgres table, which is already running, backed up, and what the Phase 2b API reads anyway.
  4. Staleness: compare timestamps (a newer load or fetch means stale), or hash the inputs and compare.
- Decision: option 3 and a hash.
  - **`model_versions`** (migration 0009): version, trained_at, data_cutoff, features_output_sha256, features_load_run_id, metrics JSONB, config JSONB, artifact_path, is_active. **One row per bundle** (win/loss and method together), so activation is one atomic switch and the serving cache key `model_version` is one string. A version registers inactive; `activate` is explicit.
  - **At most one active is enforced by Postgres**, a partial unique index on `is_active`, not by code. Switching deactivates the old row first in the same transaction, because a unique index is checked row by row.
  - **Two dates, named apart.** `data_cutoff` is the last event date the model was *fit* on (the end of its training split): it knows nothing at or after it. `config.dataset_last_event` is the last event date in the whole dataset the run read (here 2026-10-03). Today they differ by about two years, on purpose.
  - **Reproduction** is stored in `config`: seed, split boundaries and counts, feature lists and vocabularies, LightGBM parameters and best iterations, `inputs_sha256`, a hash of the odds rows used, library versions, git sha and dirty flag, and each artifact file's sha256 (so 2b can verify on load). Artifacts live under `MODEL_ARTIFACT_DIR` (gitignored), one directory per version.
  - **Determinism.** LightGBM runs with `deterministic=True`, `force_row_wise=True`, `num_threads=1` and every seed set; the swap and the bootstrap use a seeded generator. Tests train twice and require byte-identical model files. Scope: the same machine class and library versions, which is why the versions are recorded.
  - **Staleness guard.** Two things refuse training (exit 1, "run features rebuild"): `fight_features` is not one complete build (two rows for every labeled fight), or the input fingerprint the build stored no longer matches the database. Newer seed loads and newer fetches **only warn** (report `warnings`, stderr): once scraping is scheduled in Phase 5 there is nearly always a fetch newer than the last build, and a fetch that changed no input leaves the hash equal.
  - **The fingerprint** (`cageops_common.db.fingerprint`) hashes only what can change a training feature or label: completed fights (`id`, `event_id`, both fighter ids, `outcome`, `winner_id`, `method`, `scheduled_rounds`, `finish_round`, `finish_time_sec`, `weight_class`, `is_title_fight`) with their `event_date`, their fighters' `dob`, `height_cm`, `reach_cm`, `stance`, and those fights' six whole-fight stat columns. Out: identity keys, display names, `result_source`, `red_fighter_id`, `gender`, `referee`, `has_round_stats`, the stat columns the builder never reads, and all of `fight_round_stats`. Scheduled and cancelled bouts, fighters or events with no completed fight, odds, rankings, `raw_pages` and `load_runs` are not hashed, so card churn never refuses training. Every column of the four tables is classified in or out with a reason and a test fails on an unclassified one; a second test asserts the builder's read set is inside the hash, and the hash contains nothing the builder does not read.
- Found while building it:
  - **Ingestion and Wikipedia loads write no `load_runs` rows** (their run ids live in Redis); only the seed loaders and the features build do. Timestamps alone would have missed them, and `raw_pages.fetched_at` is the only Postgres footprint of a fetch.
  - **A DLQ replay re-parses cached HTML**, so fights can change with no new fetch and no timestamp moves (the D-029 edit-aliases-then-replay flow). Only a content hash sees that.
  - **No upsert path bumps a hashed column without changing data.** The four tables have no `updated_at`, counter or load-run column, and `upsert()` writes only where the row is `IS DISTINCT FROM` the new one. A test runs the real ingestion writers twice with identical data and requires an unchanged hash and unchanged row versions.
  - Checked on the real database inside rolled-back transactions: a flipped winner is refused; a newer fetch or seed load only warns; a display-name edit changes nothing.
- Tradeoff: the hash is whole rows of the columns above, so a legitimate correction anywhere in 8,771 fights makes the next train ask for a rebuild; that is the point (the rebuild was not timed, so no duration is claimed). Reading and building happen at READ COMMITTED in separate statements, so a write landing mid-build could be missed by both; ingestion is one rate-limited worker today. The guard covers training only: scheduled bouts are outside it, so **2b needs its own freshness check for predictions on upcoming fights**, and should log the active version's `features_output_sha256` at startup. There is no activation history (who switched what, when) beyond the row itself. `num_threads=1` trades speed for exact reproducibility; a whole run is about 5 s (BENCHMARKS.md), and the all-threads time was not measured. The registered artifact is train-only (D-031). Revisit when retraining is scheduled (Phase 5), or if a second model family needs the same registry.

### D-034: Defer the jerzyszocik daily odds loader
- Context: the betting-favorite baseline (D-031) uses mdabbert odds only. They end 2026-03-28, so the test year is compared on 241 of 553 fights and the 223 fights from 2026-05-17 cannot be compared at all. The Kaggle "UFC Betting Odds (Daily)" dataset (jerzyszocik, CC0, regenerated daily) is the obvious fill. Measured against our database with a read-only probe on a pinned snapshot (BENCHMARKS.md, sha256 `44fc6838...`, commit `51a2b66`), nothing loaded.
- Options considered:
  1. Load it now as a second odds source next to mdabbert and silver.
  2. Defer: keep the baseline as D-031 defined it, record what the dataset would add, and load it when grading needs it.
  3. Switch the baseline to this feed alone for 2025 and later events, keeping mdabbert for history.
- Decision: option 2. What the measurement says:
  - **Test year:** 426 of 553 fights match by name and date (0 by ufcstats id: every 2026 row has no `fight_url`), **237 of them beyond mdabbert**; the union with mdabbert is 478 (86%), up from 241 (44%).
  - **The Wikipedia period:** 162 of its 223 fights get a price, where mdabbert has none. This is the part that matters most, and the part a baseline cannot do without.
  - **Elsewhere nothing:** validation adds 0 and train adds 1 (the historical import in the file is essentially mdabbert's coverage again).
  - **Ceiling:** resolving the 46 spelling variants (by a loose, unreviewed rule) would reach 524 of 553 (94.8%); at most 529. 24 bouts are not in the feed and 5 look like replacement opponents.
  - **Quality:** the consensus favorite (last snapshot per bookmaker on or before the event, de-vigged, median 24 bookmakers) picked the winner in 304 of 426 fights (166 of 237 on the added ones) and agrees with mdabbert's favorite on 181 of 187 overlapping fights.
- The D-031 tradeoff, stated plainly: D-031 chose a single source so the baseline is one thing you can explain in a sentence, and so the comparison is on the same prices throughout. This dataset buys coverage on the test year and the first real capture time (`adding_date`, which answers the "closing line not proven pre-fight" caveat for events from 2025-07-26) at the cost of mixing sources, or of changing the baseline's source part-way through the history. Neither is wrong; each changes what "the favorite" means in every number already reported, so it should be one deliberate step with the comparison re-run, not a side effect of a loader.
- What loading would involve (so the revisit is cheap):
  - a migration: `odds.source` is CHECK-limited to `mdabbert` and `silver`;
  - a one-price-per-fight rule (the primary key is `(fight_id, source)`), such as the consensus above, or a snapshots table;
  - name and date matching for 2026 through the existing `NameResolver` with a new per-source alias scope, and about 50 reviewed alias rows (the D-029 workflow);
  - a manifest entry and a pinned snapshot (the file changes daily), a loader and tests the size of `seed/odds.py`, and `captured_at` filled from `adding_date` for live rows only (the 6,299 historical rows were all added on 2025-07-27, so their `adding_date` is not a capture time).
- Tradeoff: until then the model-versus-favorite comparison stays on 44% of the test year and is impossible for the Wikipedia period; the PR's headline ("the model loses to the favorite") rests on those 241 fights. **Revisit in Phase 5**, when grading real events needs prices for events mdabbert will never cover, or sooner if the coverage of the comparison becomes the blocker. The snapshot will be stale by then: re-download, re-run `scripts/odds_daily_probe.py`, and re-measure before deciding.

### D-035: Shared inference module, not the trainer, in the API image
- Context: the API must predict with the same model input the trainer fitted on, and its image must not carry training code (ROADMAP 2b carry-over). In 2a the feature assembly, `WinLossModel` / `MethodModel` and booster load/save lived in `cageops_trainer`, and nothing could read a bundle back: no manifest reader, no checksum verification, no "which version is active" query.
- Options considered:
  1. The API imports `cageops_trainer`. Nothing to write, and the image carries training code, its dependencies and its import-time side effects.
  2. Copy the inference code into the API. Small, and now two implementations that can drift (training/serving skew) with nothing to say so.
  3. Move the inference pieces to `cageops_common.inference`, and have both import them.
- Decision: option 3. Moved: `NUMERIC_FEATURES` and the other feature-name constants, `Vocabulary`, stance normalization, `win_loss_matrix` / `method_matrix`, `WinLossModel`, `MethodModel`, `METHOD_CLASSES`, `load_booster` / `save_booster`. New there, because 2a never had them: `bundle.py` (`Manifest`, `write_bundle`, `verify_bundle`, `load_bundle`), `rows.py` (`rows_to_arrays`, the one place a database row becomes a model input; the trainer's `load_dataset` calls it), `registry.py` (`read_active_version`). The trainer keeps fitting, vocabulary fitting, the training swap, `EXCLUDED_COLUMNS`, the dataset and the registry writes, and imports the rest with no re-export shims. numpy and LightGBM are an optional `cageops-common[inference]` extra, so the scraper and worker never pull them. `load_bundle` refuses unless the manifest exists and is for the expected version, its feature names, numeric features and method classes equal this code's constants, its `files_sha256` equals the registry's `config.artifacts_sha256`, every file's sha256 (of its bytes) matches, both boosters load, and a smoke prediction on an all-missing row has the right shapes and is finite.
- Tests: nothing under `services/api` or `packages/cageops_common` imports `cageops_trainer` (a static AST scan plus a subprocess that imports the app and asserts the module is not in `sys.modules`); the trainer's matrices equal the serving matrices for a sample of fights, and a bundle loaded the way the API loads it predicts what the trainer scored.
- Tradeoff: `cageops-common` now has a heavy optional extra and one more place a change must be reasoned about. The parity test is honest about its strength: both paths call one set of functions, so it guards re-implementation and column reordering, and the load-time feature-name check is the real runtime guard. The subprocess test checks the dev venv, where the trainer is installed; the shipped-image check is the 2b-2 CI step. The manifest has no format-version field; the feature-name equality is what would catch a change. Revisit if a third consumer appears or the bundle format changes.

### D-036: Hot reload by polling `model_versions`, not Redis pub/sub
- Context: after `cageops_trainer activate`, a running API must switch versions without a restart, finish requests already running on the old model, and never serve a model it has not verified.
- Options considered:
  1. Redis pub/sub: `activate` publishes, replicas subscribe. Instant.
  2. Each process polls `model_versions` every N seconds.
  3. Restart the API on activation (an orchestrator's job).
- Decision: option 2 (`MODEL_POLL_INTERVAL_S`, default 30). The process holds one reference (`ModelManager._current`). A request copies it into a local at its first line and uses only that local. The poller builds a complete `LoadedModel` (read, verify, load, smoke-predict) and then assigns the attribute, which is one atomic step in CPython, so a request sees the whole old model or the whole new one, and the old model is freed when its last request lets go. A replacement that fails verification is logged (`model_reload_failed`, with the version, the reason and what is still being served), counted (`api_model_reload_total{result="failure"}`) and not retried for `MODEL_RELOAD_RETRY_S` (300). The bundle is `<MODEL_ARTIFACT_DIR>/<version>`, never the stored `artifact_path` (written relative to wherever the trainer ran) and never a directory scan. With no active row at startup, or a failed verification, the API is not ready and answers 503; it never falls back to another file. If the registry later has no active row, the verified model keeps serving and a warning is logged once (`activate` is one atomic switch, so zero-active means a hand deactivation).
- Why not pub/sub: it is fire-and-forget. A replica that is restarting, or whose Redis connection blipped, misses the message and serves the old model until something else restarts it, so polling would be needed as the safety net anyway. Polling is stateless, self-healing, reads the source of truth, and keeps model loading independent of Redis (a Redis outage must not stop a reload).
- Tradeoff: up to `MODEL_POLL_INTERVAL_S` of lag, and one indexed query per replica per interval. Replicas on different versions during the lag are safe because `model_version` is in the cache key (D-042 in 2b-2). Tested: a switch with no restart; a request started before a switch finishes on the old model and one after it gets the new one; six reader threads over six switches never see a mixed model; a tampered file, a deleted file, a missing manifest and a missing directory are not ready; back-off and recovery. Revisit if a switch must be instant (then pub/sub on top of polling, not instead of it).

### D-037: `fighter_features_current`, date-relative features, and what "today" means
- Context: an ad-hoc prediction ("A against B, as of today") needs each fighter's features as of today, and `fight_features` has none: it is keyed `(fight_id, fighter_id)` and is as of each fight's own date, so a fighter's latest row leaves out their latest fight. Separately, two of the 34 model features depend on the calendar rather than on history, `age_days` and `days_since_last_fight`. A row stored yesterday is right about history and a day out on both, and `features_current` would still say true.
- Options considered:
  1. Compute features in the API request path. The API would carry history loading and `compute_features`, a second path to the point-in-time rules (and you ruled the API out of building features).
  2. A table of per-fighter features as of the build date, written by the pipeline, read by the API; store the two derived columns.
  3. The same table, but store their inputs (`dob`, `last_fight_date`) and derive them for the date being asked about.
- Decision: option 3 (migration 0010). `features rebuild` writes `fighter_features_current` in the same transaction and with the same `load_run_id` as `fight_features`, from the same `prior_fights` and `compute_features`. It has no `age_days` and no `days_since_last_fight`, and none of `weight_class`, `is_title_fight`, `scheduled_rounds` (a fight's, supplied by the matchup). `cageops_common.inference.asof.date_relative_features(as_of, dob, last_fight_date)` is stdlib-only and is called by both the builder and the API, so the rule is written once; a test shows that for several as-of dates it equals `compute_features` for the same date, and that the same stored row asked a day later moves both by exactly one. Rule 1 is tested for the new table (a fight dated today is not history, one dated yesterday is; rewriting today-and-later fights changes nothing). `fight_features`' `output_sha256` is unchanged (`5b23d187...`), so `model_versions.features_output_sha256` keeps its meaning; the report gains `fighters_current`, `current_as_of` and `current_output_sha256`.
- **"Today"** is the calendar date in `APP_TIMEZONE`, default `America/New_York`, from one function (`asof.app_today`) used by the API, by `features rebuild --today` (its default was the host's local date) and, injectably, by tests. Event dates on ufcstats and Wikipedia are US-local calendar dates and cards run into the late evening, so under UTC a Saturday card would be "in the past" from 8 pm ET and its still-scheduled bouts would count as history before their results were ingested. An event dated D is upcoming while `D >= today`; a fight dated D is history from D+1 (strictly before, D-027). `tzdata` is a dependency because slim images may lack the zone database.
- Tradeoff: the history-derived columns are only as fresh as the last rebuild, which nothing schedules yet (Phase 5), so `features_current=false` becomes the normal state after any result is ingested; that is what D-039 reports rather than hides. A fixed zone is wrong for an event whose local date differs from the US date; accepted. Two numbers per fighter are computed per request instead of read. Revisit when rebuilds are scheduled, or when events outside US time matter.

### D-038: Ad-hoc matchup context, cross-division matchups, and debut fighters
- Context: `POST /predict` takes two fighter ids and optional `weight_class`, `scheduled_rounds`, `is_title_fight`. An ad-hoc matchup is not a scheduled fight, so there is no fight row to take a division from, and some requested matchups have never shared one.
- Options considered:
  1. Default `weight_class` to NULL (LightGBM treats it as missing).
  2. Default it from the fighters' recent bouts; when they differ, pick one (the heavier, fighter A's) and say so.
  3. Default it from the recent bouts when both agree, otherwise ask the caller.
- Decision: option 3. A fighter's division is the class of their most recent bout in one of the 12 standard divisions (catch weight and open weight are one-off agreements, not a class). If both fighters' divisions are the same it is used (`weight_class_source: both_fighters_recent_bouts`); if they differ, or one has none, the answer is `422 weight_class_required`, naming each fighter's division and listing the classes the model knows, and the caller passes `weight_class`. A supplied class must be in the active model's vocabulary (14 values) or it is `422 unknown_weight_class`. NULL is not used: 11 of the 8,771 completed fights with a winner had no class, so the model's missing-class path is barely trained. `is_title_fight` defaults to false; `scheduled_rounds` to 5 for a title fight and otherwise 3; a title fight with 3 rounds is 422; unknown fields are rejected. **Of these, only `weight_class` reaches the model** (D-032 left the schedule columns out); the response says `context_used_by_model: ["weight_class"]`, and a test asserts that setting the other two changes nothing. They are validated and echoed so the day they return as features nothing about the contract moves.
- **Debuts:** a fighter with zero prior UFC fights is predicted, flagged (`has_ufc_history: false`, `n_prior_fights: 0`), and never `rates_complete`. The model has seen exactly this (every fighter's first fight is in training with NULL rates) and cards routinely include debuts.
- **A fighter with no feature row** (in `fighters`, but added after the last build) is `503 features_unavailable`: nothing honest can be computed.
- Tradeoff: a cross-division what-if costs the caller one extra field; I preferred that to a silent guess about the one input the model does use. A debut's estimate is mostly bio differences, which the flag says and nothing else does. Revisit when title and rounds become features (Phase 5), and if the frontend would rather get a suggestion than a 422.

### D-039: Freshness is not completeness, and a gap is reported, not repaired in the request
- Context: the trainer's staleness guard (D-033) ignores scheduled bouts and is about training only. A prediction needs its own answer to two different questions, which one flag would blur. On 2026-10-15: 406 fighters have a completed fight from 2026-05-17 (Wikipedia results, no per-round stats, D-025, D-029), and 442 have any completed fight without stats (the other 36 are 21 fights from the 1990s).
- Options considered (for a stale or incomplete row):
  1. Recompute in the request: right immediately, but the API needs history loading and `compute_features`, the features used are never persisted (Phase 5 cannot grade with them), and it either bypasses the cache or keys on live state.
  2. Flag it, return the stored row's prediction, and let the scheduled rebuild fix it.
  3. Refuse (409/503) when anything is stale.
- Decision: option 2, with the two questions kept apart per fighter. `features_current`: the row's `n_fights_career` equals the live count of that fighter's completed fights strictly before today (`completed_fights`, the one definition: migration 0011 added `result_source` to the view, which had been `SELECT *` frozen at creation and silently lacked it, so `stats-gap` and this check no longer repeat its predicate). It also goes false at midnight when a fight dated yesterday becomes history. `rates_complete`: `stats_gap_fights` (`n_fights_* - n_fights_with_stats_*`, for career, last 3, last 5) are all zero and the fighter has history. Never fatal, never "fresh" with a gap. `known_effect` quotes the only measured cost in the repo: on the test slice from 2026-05-17, log loss 0.6878 over 223 fights against 0.6566 over the 330 before it, a gap within noise at that size (BENCHMARKS.md); a test asserts no other figure appears. Metrics: `api_predictions_with_stats_gap_total` and `api_predictions_features_stale_total`. `features stats-gap [--since D]` reproduces the numbers (406 with `--since 2026-05-17`; 442 without it, 406 Wikipedia-only and 36 ufcstats-era).
- Tradeoff: between ingesting a result and the next rebuild, that fighter's predictions omit the new fight, in a known and labelled way; until Phase 5 schedules rebuilds that window is "whenever someone runs it". The 36 old fighters are reported as incomplete too, by window, so a caller can tell a recent gap from a 1990s one. Revisit if rebuilds become incremental enough to run per request.

### D-040: Name search is `ILIKE`, with no index
- Context: `GET /fighters?search=` needs case-insensitive substring search with a minimum length and paging.
- Options considered:
  1. `ILIKE '%q%'` as a sequential scan.
  2. `pg_trgm` with a GIN index on `lower(name)`, one migration and an extension.
  3. A normalized-name column with an index (accent folding), a migration and a backfill.
- Decision: option 1. Measured on 2026-10-15 over 2,760 fighters (BENCHMARKS.md, Phase 2b-1): the bare scan takes 0.74 to 0.86 ms, and the endpoint's whole query, with each returned row's division, fight count and last fight date, takes a median of 2.3 to 3.3 ms. `%`, `_` and the escape character in the query are escaped so a search for `100%` is a search for those characters and cannot be turned into a wildcard scan. Exact match first, then names starting with the query, then the rest, each by name and id so paging is stable. `pg_trgm` is available in the image but not enabled.
- Tradeoff: accents are not folded ("Procházka" is not found by "prochazka"), and the query is linear in fighters. Revisit at about 50,000 fighters or a p95 over 10 ms; then option 2 is one migration (`CREATE EXTENSION pg_trgm` and a GIN index), and option 3 if accent folding matters first.

### D-041: API conventions: one error shape, route-template labels, per-app metrics, pool visibility
- Context: a few small choices will be copied by every endpoint that follows, and one number (the database pool) has to be tuned from a load test rather than guessed.
- Options considered: FastAPI's default errors, raw-path labels and module-level metrics on the global registry (least code), or the conventions below, chosen once so every endpoint inherits them.
- Decision:
  - **One error shape**, `{"detail": <what happened>, "code": <stable name>}`, with extra fields where they help (`errors` on a 422, `weight_classes`, `recent_divisions`). `code` is for the frontend to branch on, `detail` is for people. 422s are rewritten into it, with the original list of problems kept in `errors`.
  - **Metric labels are route templates** (`/fighters/{fighter_id}`), read after routing; a path no route matched is one series, `unmatched`. A raw path as a label is one series per fighter id and one per URL a scanner tries.
  - **Metrics live on a per-app registry**, so a test builds an app, reads its numbers and discards it, and two apps in one process never share or double-register a series.
  - **Liveness and readiness are different questions** (D-024's stance): `/healthz` does no I/O and is 200 while the process answers; `/readyz` is 200 only with a verified model and a database that answered within three polls. Redis is reported, never a condition (the API will fail open).
  - **The database pool is visible.** Every request-path query goes through `Database.connect()`, which times the wait for a pooled connection (`api_db_pool_checkout_seconds`), counts give-ups (`api_db_pool_checkout_timeouts_total`, answered `503 database_busy` with `Retry-After`) and exposes `api_db_pool_checked_out`, `_checked_in`, `_size` and `_overflow` at scrape time. `DB_POOL_SIZE` (5), `DB_MAX_OVERFLOW` (5) and `DB_POOL_TIMEOUT_S` (30) are settings, at the values the API had before; they are guesses until the 2b-2 load test, which is why the pool is measurable now. One uvicorn process per container: no prometheus multiprocess mode.
  - **Request ids**: an inbound `X-Request-ID` is kept only if it matches `^[A-Za-z0-9-]{8,64}$`, otherwise replaced (it ends up in every log line and a response header), and one JSON access line is written per request.
  - The API's test dependency moved from `httpx` to `httpx2`, which Starlette 1.x's `TestClient` prefers (dev group only).
- Tradeoff: a custom error shape means FastAPI's default 422 body is not what clients see; a per-app registry means the default process collectors are re-added by hand. Revisit the pool numbers after the load test, and the readiness window if a database failover takes longer than three polls.

### D-042: The prediction cache: what is in the key, how long it lives, and failing open
- Context: ROADMAP 2b says to cache predictions in Redis "keyed by (fighter_a, fighter_b, model_version)". That is not enough on its own: a features rebuild, a result ingested since the build, a different matchup context and the passing of midnight all change the answer, and a cache that does not know that serves confident wrong numbers. And a cache must never make the API less available than having none.
- Options considered:
  1. The roadmap's triple.
  2. The triple plus everything else the answer depends on (below), with one canonical ordering.
  3. No cache (compute every request).
- Decision: option 2. Key: `pred:v1:{model_version}:{features_build_id}:{inputs_sha12}:{lo}-{hi}:{weight_class|auto}:{rounds}:{title}:top{n}:asof={YYYY-MM-DD}:src=adhoc`.
  - **`v1`** is the cache schema: bump it when `PredictionCore` changes shape. **`model_version`** so a new model never sees the old one's answers (and the value's own `model_version` is re-checked on read). **`features_build_id`** (`load_runs.id` of the latest features build) so a rebuild changes every number's key. **`inputs_sha12`**, the first 12 digits of `features_input_fingerprint` (D-033), so a result ingested, a bio filled in or a stat corrected since the build is a new key *before* anyone rebuilds: without it a cached `features_current: true` would go stale the moment a fight completes. **`{lo}-{hi}`**, smaller id first, so A-vs-B and B-vs-A are one entry. **Context** as requested, but the division is first validated against the active model's vocabulary and normalized to the model's own spelling (case and runs of whitespace forgiven, nothing else), *before* the key is built: two spellings of one division share an entry, a misspelling is a 422 on every request rather than a hit on a neighbour's entry, and nothing a caller typed can reach the key (the segment is also slugged to `[a-z0-9-]`). `auto` when the caller did not say: the default is a function of data the other components cover, so the key needs no database read. **`top{n}`** because the entry holds n contributions. **`asof=<date>`**, the real date in `APP_TIMEZONE`, never the word "today": age and days-since-last-fight depend on it, and an entry written at 23:59 must not be served at 00:01 (tested at New York midnight, and at UTC midnight where it must still hit).
  - **The value** is `PredictionCore` as JSON (the matchup oriented lo to hi), not the HTTP response. On read it is flipped to the caller's order by `orient()`, which is exact: B-vs-A from the A-vs-B entry equals a fresh computation of B-vs-A to the last digit (tested), because the model is always run in canonical order.
  - **Facts the key needs are polled, not read per request.** `FeaturesWatch` reads the latest build id and the live input fingerprint every `MODEL_POLL_INTERVAL_S`. The fingerprint costs about 50 ms median (BENCHMARKS.md), against about 1 ms for a count-and-max watermark; I took the fingerprint because it also notices a changed result or bio, which a count cannot, and a background 50 ms every 30 s is not on any request's path. A hit therefore costs no database round trip. `api_features_inputs_match_build` exposes the same comparison as a gauge.
  - **TTL 6 hours** (`CACHE_TTL_S`). The key invalidates; the TTL bounds what the key cannot see (a renamed fighter: names are not in the fingerprint) and Redis memory. Not shorter, so a warm run does not depend on it; not longer, so a stale display name cannot live for days. Ad-hoc entries also partition by day through `asof`.
  - **Fail open.** Every Redis call has a short socket timeout (`REDIS_TIMEOUT_MS`, 100) and no retries. Any `RedisError` or `OSError` is counted (`api_redis_errors_total{op}`), logged once per 30 s, and the request is computed uncached. After a failure Redis is not asked for 5 seconds, so a dead Redis does not charge every request the timeout (`api_cache_bypassed_total` counts those). A corrupt or foreign entry is a miss that is recomputed and overwritten. Errors and unbuilt features are never cached. Redis is never a readiness condition. `X-Cache: hit | miss | bypass` says which happened.
- Tradeoff: a change is noticed up to one poll late, so for up to `MODEL_POLL_INTERVAL_S` a cached `features_current: true` can outlive a newly ingested fight; the TTL and the poll bound it, nothing removes it. Every context field and `top{n}` multiplies entries (a caller varying `scheduled_rounds`, which the model ignores today, gets separate entries with the same numbers: correct the day the model uses it, wasteful until then). At midnight New York every ad-hoc entry is cold at once. The Redis in compose has no `maxmemory`: 2c must set one with `allkeys-lru`. Display-name edits are covered by the TTL only. Revisit when the cache hit ratio from real traffic exists (Phase 6 dashboards), and when rebuilds become scheduled (Phase 5), which makes `features_build_id` change on a clock.

### D-043: Rate limiting: a token bucket in Redis, who counts as "the client", and the frontend's path
- Context: the API is public and unauthenticated. It needs a per-client limit that still holds with several replicas (Phase 6), that cannot be dodged by lying about an address, and that does not put every user of the Next.js frontend into one bucket: server components call the API from Vercel's few server addresses, so a pure per-IP limiter would share one jar among all users, or be set so high it protects nothing.
- Options considered (algorithm): a fixed window (`INCR` + `EXPIRE`; allows twice the rate across a boundary), a sliding-window log (a sorted-set entry per request: memory grows with traffic), a sliding-window counter (approximate, no exact wait time), a token bucket.
- Options considered (the frontend): (A) raise the per-IP limit and do nothing: shared buckets, no per-user fairness, abuse through the frontend invisible. (B) a server-to-server key with its own larger bucket: one jar for all users, so one abuser exhausts everyone's. (C) a key plus the end user's address forwarded in a header, believed only with a valid key. (D) allowlist Vercel's egress ranges: not published without a paid static-IP product, and it breaks silently when they change. (E) the browser calls the API directly: works with plain per-IP limits but needs CORS and shows the API to the page; compatible with C, since a browser call is just a public-class client.
- Decision: a **token bucket** in Redis (one Lua script, atomic across replicas, reading Redis `TIME`), and option **C**.
  - **Bucket:** `RATE_LIMIT_PER_MINUTE` (120, so 2 a second) and `RATE_LIMIT_BURST` (40), starting values and not measured ones. A 429 carries `Retry-After` (whole seconds, rounded up, at least 1) and the same number in the body. Keys expire once the bucket would have refilled. The script is all-or-nothing over any number of buckets: a request refused by one is not charged by another (tested by reading the user bucket back).
  - **Exempt exactly** `/healthz`, `/readyz` and `/metrics`. Everything else is limited, including `/docs` and unmatched paths (a scanner's 404 costs a token). The limiter sits inside the request-context middleware, so a 429 is timed, logged with its client class, and labelled with its route template (looked up from the OpenAPI document, not router internals).
  - **Public clients** are keyed by IP. `X-Forwarded-For` is believed only when the immediate peer is inside `TRUSTED_PROXY_CIDRS` (empty by default: trust nothing), and then read from the right, skipping trusted proxies, taking the first address that is not one: a proxy appends the address it saw, so everything to its left is whatever the caller typed. Uvicorn runs with `--no-proxy-headers` so there is one implementation (its default trusts the header from 127.0.0.1). An IPv6 client is its whole `/64`; `::ffff:a.b.c.d` is `a.b.c.d`; a peer that is not an address shares one `unknown` bucket.
  - **Frontend:** `X-API-Key`, compared with `hmac.compare_digest` against `FRONTEND_API_KEY` (and `FRONTEND_API_KEY_PREVIOUS`, for a rotation overlap); a key under 32 characters is not a key (the class is disabled, one warning at startup). A valid key gets two buckets: one per end user, keyed by `X-CageOps-Client-IP` (300 a minute, burst 100), and one ceiling for the whole key (6,000, burst 600). **The forwarded address is believed only with a valid key**; without one it is ignored and counted (`api_ratelimit_ignored_headers_total`), so it can neither dodge a limit nor spend another address's bucket. A malformed address leaves only the ceiling. Settings are `SecretStr`: the key is never in a log line, a metric label, a response or a `repr` (tested by searching all of them). It belongs in Vercel's server-side environment, never `NEXT_PUBLIC_*`, and travels only over TLS (2c). Sending the header from the frontend is Phase 3.
  - **Redis down: fail open.** The request is allowed, `api_redis_errors_total{op="ratelimit"}` counts it, and the cache and the limiter share one `RedisGuard` so a dead Redis is left alone for 5 seconds instead of costing every request its 100 ms timeout. The limiter protects capacity, not correctness; failing closed would turn a Redis blip into a total outage of a public read-only API.
- Tradeoff: a client behind one NAT shares an IPv4 bucket (the public class cannot tell them apart). A leaked frontend key lets someone spoof end-user addresses, but never beyond the key-wide ceiling, and rotation is one environment change. `Retry-After` is in whole seconds, so a client may be told 1 second when 100 ms would do. With Redis down there is no limit at all. **Revisit in Phase 4:** the LLM writeups cost money, so those routes should fail closed or fall back to a small in-process limiter. The defaults are guesses until real traffic exists (the load test runs with the limiter off, and says so).

### D-044: Upcoming bouts: no scheduled-fight job, because the page has no round count
- Context: the 2a carry-over (ROADMAP, D-032) asked 2b to fill `is_title_fight` and `scheduled_rounds` for upcoming bouts and write them into `fight_features`, so Phase 5 could bring them back as features. What was known on 2026-10-15: the database holds no scheduled bouts (the only source of upcoming cards is ufcstats, which is behind the challenge, D-025, and `scrape-upcoming` is refused for Wikipedia, D-029); the ufcstats upcoming *event* page carries fighters and weight class only (D-023); each bout row links to a fight-details page that `fetch_event` never fetches. `features rebuild` already copies `fights.is_title_fight` / `scheduled_rounds` into `fight_features` for scheduled bouts, so the only missing piece was a source. Whether an upcoming fight-details page carried either field was unverified. The plan made it a gate (Gate G): build the job only if two hand-saved pages (a title bout, a non-title bout) both show a parseable round count and a populated bout heading.
- Options considered:
  1. A `fetch_scheduled_fight` job and writer that fill both columns from the fight-details page.
  2. A title-only job: a new upcoming-page parser and writer for `is_title_fight`, leaving `scheduled_rounds` NULL.
  3. Derive `scheduled_rounds` from the title flag (title means 5 rounds, otherwise 3).
  4. Build nothing; leave both NULL and record why.
- Decision: option 4. Evidence (two pages saved from a browser on 2026-10-15, UFC 333; minimized copies in `services/scraper/tests/fixtures/ufcstats/upcoming_fight_pages/`, pinned by `tests/parsers/test_upcoming_fight_page.py`):
  - **The title marker is there:** the title page's bout heading reads "UFC Featherweight Title Bout" and has a belt image; the other reads "Flyweight Bout" with no belt.
  - **The round count is not:** neither page has "Time format", any "Rnd" text, or the Method / Round / Time / Referee block at all. An upcoming fight page is a "Matchup / Tale of the tape" layout (records, average fight time, height, reach, stance, DOB, per-minute averages); the result block, which holds the round format, exists only after the fight.
  - **The existing parser cannot read these pages:** `parse_fight` raises `ParseError: unknown result badge ''` on both, so even a title-only job needs a new parser.
  - The tale-of-the-tape numbers are scrape-time snapshots (the D-008 leak) and are not to be used as features.
  - Option 1 fails the gate on the rounds half. Option 3 would label a non-title main event (5 rounds) wrongly and is a default, not data: `scheduled_rounds` is never defaulted. Option 2 is a real parser, job, writer and tests for one column the model does not use (D-032), that could only run on fixtures while ufcstats is gated, and D-032 measured the benefit of the two columns together, not of the title flag alone.
- Consequences: `is_title_fight` and `scheduled_rounds` stay NULL for scheduled bouts, and `/events/upcoming` reports NULL for both (never `false`, never 3). Nothing else changes: if a source ever fills the `fights` columns, `features rebuild` already carries them into `fight_features`. **Phase 5 cannot bring either column back as a feature** until a source supplies both before the fight, or serving would feed the model NULLs it never saw in training (ROADMAP note added).
- Tradeoff: the carry-over stays open, and the 0.006 validation log loss it was meant to recover (D-032) stays unrecovered. The title flag is a known, available fact, so **a title-only parser is a documented option** if a rounds source appears (another site, a ufcstats export, or an allowlisted User-Agent, D-025); with both columns available the original plan applies unchanged. The pinned test fails if ufcstats starts putting a round format on upcoming pages, which is the signal to reopen this entry.
